# 公众号式项目深描（参考风格）

> 参考来源：技术类公众号对开源项目的深度介绍——痛点清晰、能力分层、数据背书、场景落地，让读者觉得「这个项目很厉害」。  
> 我们**保留**现有「技术趋势栏目主编」开场（thesis + 日榜证据），**项目段**采用本 reference 的深描结构。

微信公众号正文无法自动抓取时，按下列结构写，不要写成干巴巴的功能列表。

## 每个入选项目必须输出的 Markdown 块

在 `## 入选项目` 下，除链上角色外，每个项目增加 **`### 项目深描：owner/repo`** 小节：

```markdown
### 项目深描：owner/repo

**一句话定位**（≤20 字，像公众号标题副句）

**解决什么问题**
- 过去开发者/团队怎么做？痛点是什么？（2–3 句，具体场景）
- 为什么现在这个问题被放大？（趋势、成本、合规、规模）

**它怎么做的**（机制，不是营销）
- 核心能力 1：…
- 核心能力 2：…
- 核心能力 3：…（可选）
- 与同类方案的关键差异（1 句）

**为什么现在上热榜**
- 排名 #{n}，Star {x}（来自日报，勿编造）
- 作者/组织背景（若日报有）
- 与本期 thesis 的关系（1 句）

**落地场景**
- 谁应该用：个人开发者 / 小团队 / 企业平台…
- 典型用法：…
- 边界/限制：…（必须有，体现专业）

**口播压缩版**（25–35 秒，纯口播，无标记）
{把上面压缩成一段可直接念的项目介绍，保留「痛点→能力→意义→证据」顺序}
```

## 口播中的项目段顺序（与画面配合）

SOP 视频（video-pipeline）每个项目两段口播：

1. **深描段**（concept_card / intro_card）：用「口播压缩版」的前半——痛点 + 核心能力 + 为什么厉害。
2. **证据段**（github_scroll_callout）：Star、README 亮点、排名——与深描段不重复堆砌。

MPT 视频只有口播+字幕，**更依赖「口播压缩版」** 的信息密度；仍须来自日报真实项目，禁止换成无关热门仓库。

## 语气与禁忌

**要像**：

- 先讲「为什么需要」，再讲「它怎么解决」。
- 用类比降低理解成本，但保留 1–2 个技术关键词（如 RAG、Skill、MCP）。
- 用数据（Star、排名、语言占比）做背书，数据必须来自日报/API。

**不要**：

- 「神器」「爆火」「好家伙」堆情绪。
- 编造 Star、用户量、大厂背书。
- 只列功能 bullet 不讲场景。
- 每个项目同一套「第一个/第二个」句式。

## 示例（结构示意，项目名替换为当日真实仓库）

**痛点**：过去 Agent 的能力靠临场 Prompt，团队无法复用，上线一次改一次。

**能力**：把最佳实践固化成 Skill 文件，版本管理、可审计、可组合。

**意义**：这是从「个人技巧」到「工程资产」的分水岭；热榜里同时出现标准层、工具层、运行时，说明行业在补这一环。

**证据**：今日 Trending 第 2，Star 12k，Python 为主，README 强调 open spec。

## 与 `style-guide.md` 的关系

- `style-guide.md`：人设、叙事链、禁止项。
- 本文件：**单个项目的深度介绍密度**，供 `## 入选项目` 与 `完整口播文本` 共用。
- 开场 thesis、趋势链、收尾长期判断仍按 style-guide，不削弱。
