# 06. 客户端与框架集成

## 先把 UI 当作 ChatClient 的投影

`@tanstack/ai-client` 是真正的客户端状态机。React、Vue、Solid、Svelte、Preact 和 Angular 包主要负责订阅状态、提供框架友好的 API 和可选 UI，不应各自重新实现流协议。

```mermaid
flowchart LR
  App[Framework component] --> Hook[useChat / composable / signal]
  Hook --> CC[ChatClient]
  CC --> Conn[ConnectionAdapter]
  Conn --> Server[chat() endpoint]
  Server --> Events[StreamChunk]
  Events --> Proc[StreamProcessor]
  Proc --> State[UIMessage / run / tool / interrupt state]
  State --> Hook
  Hook --> App
```

## ChatClient 的主要职责

`ChatClient` 负责：

- 维护 `messages`、当前 Run、连接状态、error、usage 和生成状态。
- 通过 `ConnectionAdapter` 发送消息并消费流。
- 把 `StreamChunk` 增量应用到 UIMessage parts。
- 管理 server/client tools、typed tool input/output 和 approval。
- 处理 queue/busy strategy，决定用户忙碌时排队或拒绝。
- 保存和恢复 transcript、pending interrupt、resume pointer。
- 处理 stop、abort、detach、rejoin 和 resumable connection。
- 暴露 `resolveInterrupts()`、`resumeInterruptsUnsafe()` 等恢复边界。

它不负责：

- 证明用户拥有 `threadId`。
- 替服务端执行敏感工具。
- 替应用实现数据库写入、权限和业务幂等。
- 自动保证事件源具有 durable delivery。

## Connection Adapter 选择

| 适用场景 | Adapter |
|---|---|
| 普通浏览器到 HTTP 服务 | `fetchServerSentEvents()` |
| 不适合 SSE 的代理/runtime | `fetchHttpStream()` |
| 一次性 JSON 请求 | `fetchJson()` |
| React Native / Expo | `xhrServerSentEvents()` 或 `xhrHttpStream()` |
| 同进程 `chat()` / server function | `stream()` |
| async fetcher / RPC | `fetcherToConnectionAdapter()`、`rpcStream()` |
| 长连接、多 Run、双向交互 | `webSocket()` |
| BroadcastChannel / SharedWorker / 自定义协议 | `subscribe` / `send` 自定义适配器 |

所有 adapter 需要处理 `AbortSignal`。`useChat().stop()` 应触发 abort；自定义 adapter 如果不尊重 signal，UI 会看似停止但服务端 Run 仍可能继续。

## `useChat` 的状态心智模型

以 React 为例，`useChat` 是 `ChatClient` 的框架绑定：

```ts
const {
  messages,
  sendMessage,
  stop,
  status,
  error,
  pendingInterrupts,
} = useChat({
  connection: fetchServerSentEvents('/api/chat'),
})
```

发送消息后，Hook 不是等待一个完整 string promise；它订阅增量状态：

1. 用户消息进入本地 transcript。
2. Client 创建或标记 Run，调用 connection。
3. 文本部分增量更新同一个 message ID。
4. Tool Call part 从 args 字符串逐步变为 parsed input。
5. Tool result / approval / reasoning / structured output 写入对应 parts。
6. `RUN_FINISHED` 标记 Run 终点，UI 获得稳定状态。

可选 `/ui` 子路径提供 `Chat`、`ChatMessage`、`ChatInput`、`ToolApproval` 等组件，但应用也可以直接使用 headless 状态自绘。

## UIMessage 与 ModelMessage 转换

`UIMessage` 是 parts-based UI representation，例如：

```text
UIMessage
  ├── text part
  ├── thinking part
  ├── tool-call part
  ├── tool-result part
  ├── structured-output part
  ├── activity part
  └── subagent part
```

`ModelMessage` 更接近 Provider history：`role`、`content`、`toolCalls`、`toolCallId`、`thinking`、metadata。转换器需要维护：

- 工具调用参数的原始 JSON 字符串与解析 input。
- Provider thinking signature / redacted thinking。
- 文件、图片、音频、视频和 UI resource。
- Persisted message ID 和 createdAt。
- AG-UI metadata 与 Provider-specific tool metadata。

持久化后恢复时，message ID 不能随意重生成，否则客户端会把同一个流中的消息画成新的气泡，或无法把新增量合并到原 message。

## Interrupt 客户端状态

`ChatClient` 从 `RUN_FINISHED.outcome.interrupt` 建立 pending interrupt：

```text
pending interrupt
  → bind to known tool / generic definition
  → draft input or response
  → validate local shape
  → submit complete batch
  → server validates all
  → continuation run
```

UI 只应提供明确的状态：pending、draft、submitting、resolved、cancelled、invalid/generic。不要仅以 `needsApproval` 布尔值推导真实状态。

当页面刷新或组件卸载：

- 普通 abort 可能结束 Run。
- detach 模式可保留服务端 Run，后续按 run/thread 重新加入。
- persistence 可保存 resume snapshot，让新实例知道 pending interrupt 和要 rejoin 的 Run。
- delivery durability 只负责重放事件 offset，不能代替 interrupt snapshot。

## 队列与并发

`ChatClient` 需要决定用户在 Run 进行中再次发送消息的策略：

- `reject`：忙时拒绝。
- `queue`：保存 `QueuedMessage`，当前 Run 完成后发送。
- 自定义策略：按 busy reason、interrupt、subagent 或 detach 状态做路由。

队列项要保留输入的完整语义（文本、多模态 content、客户端上下文），而不是只保存一个输入框 string。服务端仍应重新做权限和 schema 校验。

## Generation Client 与 Realtime

Client Runtime 不只负责 Chat：

- `GenerationClient` 订阅图片、音频、语音、转录、摘要、视频等活动的进度和结果。
- `RealtimeClient` 使用 Realtime Adapter，处理 session、token、audio events 和 connection 生命周期。
- 这些活动共享活动类型和持久化/重建原则，但不应强行塞进 Chat 的 tool-call message model。

## BYOK

BYOK（Bring Your Own Key）允许客户端或应用按选定 Provider/模型提供 key。它改变的是 adapter key resolution，不改变 ChatClient 的事件、工具、审批和持久化契约。

安全边界：

- 浏览器 BYOK 只能用于用户明确接受暴露 key 的场景。
- 服务端 Provider key 应通过环境变量、secret store 或应用 auth 注入。
- `scrub` / key resolver 不能成为租户权限判断的替代品。

## 框架适配的设计规则

新增框架包时保持以下顺序：

1. 先让 `@tanstack/ai-client` 的行为和类型成立。
2. 用框架的原生响应式机制订阅 ChatClient，不复制 reducer。
3. 暴露该框架习惯的 hook/composable/signal，但保留可扩展的 headless 逃生口。
4. 若提供 UI，使用主包 `/ui` 导出并覆盖 Tool Approval、错误、thinking、资源等状态。
5. 加类型测试和真实流 smoke，不只测试静态渲染。
