# 09. 测试、发布与变更指南

## 先找到正确的验证层

TanStack AI 的风险不只在函数返回值。一次变更可能同时影响类型推导、Provider wire、AG-UI 事件、客户端状态、恢复、多个框架和 E2E。因此测试应跟随边界，而不是只跑一个 package 的单元测试。

## 测试分层

| 层 | 主要验证 | 目录/命令 |
|---|---|---|
| Unit | parser、schema、事件归一化、工具、middleware、状态机 | `packages/*/tests`、`src/*.test.ts`；`pnpm test:lib` |
| Type | Provider model capability、tool input/output、framework API | 各包 `tests/*types*.test.ts`；`pnpm test:types` |
| Wire | Provider 请求映射、usage、reasoning、tools、structured output | Provider 包 tests |
| Conformance | Persistence/Sandbox/Store 的共同契约 | `ai-persistence/src/testkit`、`ai-sandbox/src/testkit` |
| E2E | 服务端 + transport + client + UI 的完整流 | `testing/e2e/tests`；`pnpm test:e2e` |
| Docs | 内部链接和文档生成一致性 | `pnpm test:docs` |
| Build/publish | Nx build、publint、exports、声明文件 | `pnpm test:build`、`pnpm test:dts` |

根 `package.json` 中的完整 CI 会额外运行 sherif、knip、oxlint、kiira、maintainer checks 等。不要把本地包测试通过当作完整验证。

## 高风险变更矩阵

### 修改 `chat()` / TextEngine

必须覆盖：

- 无工具文本流。
- 多轮 Agentic Tool Loop。
- 并行 Tool Calls。
- Client Tool / Server Tool。
- Approval 与 Generic Interrupt。
- abort、disconnect、provider error。
- structured output（独立 finalization 和 combined）。
- subagent 与 persisted resume。

主要文件：`activities/chat/index.ts`、`tool-calls.ts`、`interrupt-*.ts`、`stream-to-response.ts`。

### 修改公共事件或消息转换

必须覆盖：

- `StreamChunk` 的 AG-UI compliance。
- SSE、HTTP、JSON、WebSocket、in-process。
- StreamProcessor 的 START/CONTENT/END 和 CHUNK 两种形态。
- UIMessage ↔ ModelMessage 的 round-trip。
- thinking signature、文件和多模态资源。
- 中断 terminal 的 snapshot 与 metadata。

### 修改 Provider

必须覆盖：

- request wire（system/messages/tools/options）。
- model metadata 和 tool capability。
- stream chunk、usage、finish reason。
- reasoning / signed content。
- structured output。
- 429/retry-after、超时和 abort。
- provider-specific tool 和文件来源。

### 修改 Persistence / Durability

必须覆盖：

- overwrite transcript、分页和 merge。
- active run、error、abort 和 terminal。
- interrupt store 全批次提交、重复提交和恶意 payload。
- reconstruct 后的 message IDs、createdAt、tool correlation。
- delivery offset 去重、重连无进展上限、截断。
- best-effort activity sidecar 不影响主 transcript。

### 修改 Sandbox / Code Mode

必须覆盖：

- tool binding 类型生成、代码 strip/validation。
- Promise 并行和错误传播。
- abort、超时、内存/网络 policy。
- process spawn/kill、fs/git、workspace 生命周期。
- capability 声明与 provider 行为一致。
- journal/checkpoint/reclaim/reap、跨 provider conformance。

## 推荐变更流程

1. **读边界**：先看本目录对应章节、目标包 README、`AGENTS.md`、`CONTRIBUTING.md` 和邻近测试。
2. **画影响面**：列出 Core、Provider、Client、Framework、Persistence、E2E 中会触及的边界。
3. **改最窄的层**：Provider 差异留在 Provider；UI 状态留在 Client；存储通过 Store/Middleware，不把宿主数据库塞进 Core。
4. **先写失败测试**：优先覆盖 wire/event/state 的不变量，再实现。
5. **跑分层验证**：目标包 unit/type → 相关 E2E → docs/build；跨包改动再跑 `test:pr`。
6. **检查 exports 和变更集**：发布包新增入口、声明文件、changeset、README/API docs 都要同步。

## 常用命令

```bash
# 安装依赖
pnpm install

# 构建所有公共包
pnpm run build:all

# 单元、类型、构建和文档
pnpm test:lib
pnpm test:types
pnpm test:build
pnpm test:docs

# 端到端
pnpm --filter @tanstack/ai-e2e test:e2e

# 受影响项目的完整 PR 检查
pnpm test:pr
```

仓库规则要求使用根目录固定的 pnpm 版本。不要为了让测试通过随意更新 lockfile、绕过 Nx affected、关闭 E2E 或修改生成文档而不记录原因。

## 源码阅读顺序

按问题选择最短路径：

| 问题 | 阅读顺序 |
|---|---|
| 模型为什么多调了一轮 | `chat/index.ts` → `agent-loop-strategies.ts` → structured output 分支 |
| 工具为什么没有执行 | `tool-calls.ts` → interrupt resume → client `chat-client.ts` |
| 浏览器为什么少一段 token | `connection-adapters.ts` → `StreamProcessor` → message reducer |
| 断线后为什么不能恢复 | `stream-to-response.ts` → `stream-durability.ts` → client reconnect tracker |
| 刷新后消息丢失 | `ai-persistence/middleware.ts` → Store contract → reconstruct |
| Provider 请求错误 | provider `adapters/text.ts` → `BaseTextAdapter` → wire tests |
| Code Mode 不安全 | `ai-code-mode` → `ai-sandbox/contracts.ts` → isolate/provider capabilities |

## 设计评审问题

提交评审前只问这五组问题：

1. **边界**：这个状态由谁拥有？Core、Client、Provider、App、Store 还是 Transport？
2. **协议**：是否仍输出合法 AG-UI 事件？是否保留 run/thread/tool/message correlation？
3. **恢复**：重连、重试、刷新和中断续接时会不会重复副作用或丢状态？
4. **类型**：Provider model capabilities、schema、client tool output 是否在编译期和运行时都校验？
5. **安全**：是否引入了客户端信任、跨租户 transcript 读取、未授权工具、secret 泄露或未隔离执行？

## 这份架构文档的维护规则

源码提交变化后，优先更新：

- `README.md` 的快照提交、日期和目录。
- 包地图和架构边界。
- 受影响的事件、恢复、工具或持久化章节。
- `CODE_MAP` 等导航（如果后续新增）。

文档中的源码路径以 `../../ai/...` 指向本地工程。若路径、包名或公共事件已经改变，应优先修正文档，不要留下“看起来合理但无法打开”的链接。
