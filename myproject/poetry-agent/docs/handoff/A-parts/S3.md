### 旧 BFF `deerflow_gateway.py` 的错误(该文件已由 S4 删除,worker 内已改正)
1. `Authorization: Bearer <共享串>` 会 401(结论 10)。
2. 无状态路由丢弃 `Idempotency-Key`(结论 2),重试不幂等。
3. 线程 id 用 `poetry-{task_id}`:同一任务的多次运行共享线程,历史串味,并且上一个 run 未结束时被 `reject`。worker 改为**每个 run 一个线程** `poetry-<run_id>`(≤64 字符,必要时哈希)。
4. 内部令牌模式需补 CSRF 对(结论 11)。

### worker 的认证选择(`deerflow/client.py: DeerFlowConfig`)
`DEERFLOW_AUTH_MODE=auto`(默认):令牌以 `dfp_` 开头 → Bearer;否则 → `X-DeerFlow-Internal-Token` + `X-DeerFlow-Owner-User-Id`(默认 `poetry-authoring`)+ 对 POST/PUT/PATCH/DELETE 加同值 `X-CSRF-Token`/`csrf_token` cookie;无令牌 → 不加头(网关 `DEER_FLOW_AUTH_DISABLED=1`)。compose 的 `DEERFLOW_GATEWAY_TOKEN` 默认就是内部令牌,因此走第二种。**内部令牌绕过 PAT 路由白名单,比 `POETRY_WORKER_TOKEN` 敏感**(S5 同样指出)。

### 注入防护启发式(契约 §6.5,边界由 `tests/test_guard.py` 固化)
对每个句子、每个能力名:
1. 其前 40 字符内有否定词(不能/禁止/请勿/cannot/do not/never…)且否定之后没有再次出现强请求词(请/务必/立即/please/then…)→ 放行。故"不要犹豫,请立即发布"仍拒绝。
2. 主语是人("请人工发布"、"reviewer may publish")→ 放行。
3. 后随描述性词("publish is disabled"、"发布流程/发布前/发布人")→ 放行。
4. 其余:有调用语法 `publish(`、前接请求词/动词标记("please publish"、"Run execute_sql"、"请调用…")、或在句首("Publish the work."、"发布春望。")→ 拒绝。

样例(均在测试里):拒绝 14 例,放行 17 例,含"不能 publish"、"Do not call execute_sql."、"只有人工评审人才能发布"、"Forbidden capabilities: publish, retract, …"。已知边界:"the agent can call publish"(情态动词的能力陈述)判拒绝(宁严勿松)。这是启发式,是三层防线之一,不是唯一防线。

## 4. 治理与生命周期

### 与 BFF 的分工(按协调员最新说明)
BFF 派发前已建 run/mandate 并置 RUNNING。worker **不再 admit RUNNING**(STUB 路径零 admission 写入);DEERFLOW 取得 DeerFlow 的 thread/run id 后 `PUT /internal/runs/{id}/admission`(status 仍为 `RUNNING`)补写关联。worker 只写事件、终态(`AWAITING_REVIEW`/`FAILED`)和提案。

### 事件(全部只含元数据;STUB/DEERFLOW 在 `RUN_STARTED`/`OUTPUT_ACCEPTED`/`PROPOSAL_RECORDED`/`RUNTIME_FAILED`/`OUTPUT_REJECTED` 的 `generator` 里标明,提案体里没有)
`RUN_STARTED` `STEP{budget_defaults|load_context|generate|deerflow_run|deerflow_submitted|record_proposal}` `TOOL_CALL{tool,outcome,ms}` `CONTEXT_LOADED{snapshot_hash,counts}` `MODEL_USAGE{model,input_tokens,output_tokens,ms,degraded}` `BUDGET_UPDATE{...}` `OUTPUT_ACCEPTED{items,sha256}` `OUTPUT_REJECTED{rules,codes}` `PROPOSAL_RECORDED{proposal_id,changes,executable}` `RETRY{attempt,reason,target,op}` `CIRCUIT_OPEN{target,reopens_in_s}` `RUNTIME_FAILED{reason}` `RUN_CANCELLED{by,stage}`。

### 状态流转
成功 → 先 `POST /internal/proposals`(幂等键 `worker:proposal:<run_id>`,`proposal_id=proposal_<run 后缀>`),再 `PROPOSAL_RECORDED` 事件,再 `PUT state AWAITING_REVIEW`。只读报告也有 ≥1 条 `GAP_REPORT` 变更(`compile` 兜底),所以不会走 `COMPLETED`。失败 → `RUNTIME_FAILED` + `FAILED`;输出被拒 → `OUTPUT_REJECTED` + `FAILED`(不另发 `RUNTIME_FAILED`)。**DeerFlow 失败一律 FAILED,不降级为 STUB(D4)**,测试覆盖。

### 取消(按协调员说明)
BFF 先调 worker `cancel`,成功后自己写 FAILED、**不写** `RUN_CANCELLED`。所以 worker 收到取消时:先置"静默"位,再唤醒睡眠/轮询,然后**恰好追加一次** `RUN_CANCELLED`(等任何在途写完成),此后该 run 不再写任何事件、状态、提案;取消后到达的模型输出整体丢弃;同时尽力取消 DeerFlow 侧 run。未知 run(如 worker 重启过)也追加一次并记墓碑,之后同 id 的派发返回 duplicate。已结束的 run 取消不写任何东西。进程关闭(`shutdown`)走另一条路:未完成的 run 记 `RUNTIME_FAILED{WORKER_SHUTDOWN}` + `FAILED`,不冒充用户取消。

### 重试 / 熔断 / 预算
- budgets.yaml v2:`per_task_type` 覆盖顶层;真实 `deerflow-profile/config/budgets.yaml` 解析无任何默认项。缺文件/缺字段 → 保守默认并发 `STEP{budget_defaults}`。
- 重试:仅对可重试错误(网络、超时、5xx、429、畸形 JSON),退避 `[2,5,15]`;4xx 立即失败且不计入熔断。熔断:连续 `failure_threshold` 次失败后打开,`open_seconds` 后半开;打开期间对网关**零请求**。熔断器是进程级共享的。
- 预算:墙钟(超时→取消远端 run→`WALL_TIMEOUT`)、工具调用数(数 `llm.tool.result`;STUB 里每次桥读取算一次)、token(按 AI 消息累计,结束时与 run 行对账)、输出字数。
- **备用模型(协调员 #2)**:`DEERFLOW_FALLBACK_MODEL`(默认空 = 关闭)。仅当主模型那次尝试以 `DEERFLOW_RUN_ERROR` 或 `MODEL_ERROR_FALLBACK` 失败、且未取消、预算未耗尽时,**显式**用新线程 `poetry-<run>-fb` 和 `context.model_name=<备用>` 重提一次(幂等键后缀 `-fb`),发 `RETRY{reason:"MODEL_FALLBACK:…",op:"switch_model"}`,其后所有 `MODEL_USAGE.degraded=true`。认证/冲突/格式错误不触发换模型;只换一次。不假设网关会自动回退。**compose 里没有这个环境变量,是否启用由用户/S5 决定。**

| 1 | 用线程作用域路由而非 `POST /api/runs/stream`;每 run 一个线程 | 只有它支持幂等键;避免历史串味(§0) |
