## 0. 需要你先看的发现(按严重程度)

### 0.1 网络: 现有 `internal: true` 会让整条链不通(单独发现,已修)
原 `compose.yaml` 只有一个网络 `poetry-agent-internal`,并设了 `internal: true`。
- Docker 对 `--internal` 的定义: "Restrict external access to the network";容器之间可通,但 "no default route is configured",去往其它网络的流量被防火墙规则丢弃(docs.docker.com/reference/cli/docker/network/create,2026-11-06 读取)。Compose 文件参考只写了 "an externally isolated network"。
- 推论(**未实机验证**): ① `deerflow-gateway` 访问 `POETRY_LLM_API_BASE`(明文 http,容器外)不通;② `poetry-domain-mcp` 访问宿主机 Java API(`host.docker.internal`)不通;③ `agent-bff` 要直连 Java studio 端点同样不通;④ 仅挂在 internal 网络上的服务**发布的端口宿主机可能不可达**。第 ④ 点 Docker 文档没有明说,我没有实机验证,只能说"文档没承诺它可达,按风险处理"。
- 修法: 保留 internal 网络(服务互通,不出网),新增普通 bridge `poetry-agent-egress`,只加给必须出网的服务:
  | 服务 | internal | egress | 原因 |
  |---|---|---|---|
  | agent-bff | 是 | 是 | 直连 Java studio;向宿主机发布 8100 给 Studio |
  | poetry-domain-mcp | 是 | 是 | 访问 Java API |
  | deerflow-gateway | 是 | 是 | 访问模型网关 |
  | agent-worker | 是 | **否** | 只访问 MCP 与网关,且不持有模型密钥 |
  | redis | 是 | **否** | 只被网关用 |
- BFF、MCP 加了 `extra_hosts: host.docker.internal:host-gateway`(Linux 需要;Docker Desktop 自带)。
- 残留风险: 网关与 BFF 现在同在 egress 网络,BFF 在网络层能连到 `deerflow-gateway:8001`。BFF 不再持有网关令牌(只有 worker 有),网关鉴权(见 0.4)是唯一的拦截。想更严可以把 gateway 的 egress 换成只给它一个独立网络。

### 0.2 `"Bearer $POETRY_DOMAIN_MCP_TOKEN"` 不会被 DeerFlow 展开(原配置的真 bug,已修)
- `harness:config/extensions_config.py:566-595`: 只有**整串以 `$` 开头**才展开,否则原样返回。`df:backend/docs/MCP_SERVER.md`(Parallel Search 一节)明说 "DeerFlow expands only whole-string `$ENV_VAR` references, not `Bearer $ENV_VAR`"。所以原配置会把字面量 `Bearer $POETRY_DOMAIN_MCP_TOKEN` 发给 MCP,MCP(`poetry_domain_mcp/server.py:527-531`,要求 `authorization == "Bearer <MCP_INTERNAL_TOKEN>"`)必然 401。
- 修法: extensions_config 写 `"Authorization": "$POETRY_DOMAIN_MCP_AUTHORIZATION"`;compose 里给网关拼好 `POETRY_DOMAIN_MCP_AUTHORIZATION: Bearer ${POETRY_DOMAIN_MCP_TOKEN}`。k8s 里这个变量由网关 Secret 以完整值提供。
- 另: `config.yaml` 的 `$VAR` 缺失会让配置加载**直接抛错**(`harness:config/app_config.py:655-659`),而 extensions 是缺失变得空串(`extensions_config.py:578-585`)。所以 compose 总是给 `POETRY_LLM_*` 定义(`${VAR:-}`,可为空)。

### 0.3 skills 在原挂载方式下根本不会被发现,且原 frontmatter 会被静默丢弃
- 加载器只扫 `<skills 根>/{public,custom,legacy,...}/<name>/SKILL.md`(`harness:skills/storage/local_skill_storage.py` `_iter_skill_files`,L75-;`SkillCategory` 见 `harness:skills/types.py:10-22`)。原 compose 挂 `…/skills:/app/skills:ro`,得到 `/app/skills/<name>/SKILL.md`,不在任何类别目录下。修为挂到 `/app/skills/public`(同时遮蔽镜像自带的 ~20 个上游 public skill)。
- `parse_skill_file` 对缺 `name` 或缺 `description` 直接返回 None(`harness:skills/parser.py:252-256`)。原四个 skill 只有 `name`+`version`,**没有 description**,即使被扫到也会被跳过。已补。
- 允许的 frontmatter 键见 `harness:skills/frontmatter.py:15-27`(含 `version`、`allowed-tools`);description 不得含 `<`/`>` 且 ≤1024(`harness:skills/validation.py:68-80`),已遵守。`allowed-tools` 在 DeerFlow 里只是兼容元数据,**不限制工具**(`harness:agents/lead_agent/prompt.py:945-947` 的说明),真正的限制是 guardrails。

### 0.4 网关认证: 文档里写的 `Authorization: Bearer` 与网关实际接受的不一致(需要 S3 处理)
- 网关接受三类凭据(`df:backend/app/gateway/auth_middleware.py:98,140-205`): ① `X-DeerFlow-Internal-Token` = `DEER_FLOW_INTERNAL_AUTH_TOKEN`(`app/gateway/internal_auth.py:14-16,38-40`;`AUTH_DESIGN.md` "Internal Auth" 一节);② `Authorization: Bearer <PAT>`,但 PAT 是网关用户表里的真实令牌,不是任意共享串,且路由受 `is_pat_allowed_route` 约束(`app/gateway/auth/pat.py:123` 允许 `POST /api/runs/stream`);③ 浏览器 cookie。
- `docs/deerflow-integration.md` 说 BFF 发 `Authorization: Bearer ${DEERFLOW_GATEWAY_TOKEN}`。除非该值是网关里签发的 PAT,否则会 401。**建议 worker 用方案 ①**: 发 `X-DeerFlow-Internal-Token: <DEER_FLOW_INTERNAL_AUTH_TOKEN>`,可选 `X-DeerFlow-Owner-User-Id: poetry-authoring`。compose 里 worker 的 `DEERFLOW_GATEWAY_TOKEN` 默认就取 `DEER_FLOW_INTERNAL_AUTH_TOKEN`(`${DEERFLOW_GATEWAY_TOKEN:-${DEER_FLOW_INTERNAL_AUTH_TOKEN:-}}`)。
- 内部令牌是"全权令牌"(绕过 PAT 路由白名单)。worker 持有它,gateway 在内网,可接受;但它因此比 `POETRY_WORKER_TOKEN` 更敏感。
- 另: `AGENT_ID` → `agent_name` 的规范化是 小写、`_`→`-`(`app/gateway/services.py:1311-1325`),`poetry-editor-lead` 已合规。

### 0.5 DeerFlow 2.2.0 没有"主模型失败自动切备用模型"
我在 `harness:` 与 `df:backend/app` 全量检索 fallback/failover,只有: ① `_resolve_model_name`(`agents/lead_agent/agent.py:228-240`): 请求的模型名**不存在**时退回 `models[0]`;② LLM 错误处理中间件的重试 + 熔断(`agents/middlewares/llm_error_handling_middleware.py:463-464,528-`,配置 `circuit_breaker`/`llm_call`,`app_config.py:310-311`)。没有"调用失败 → 换另一个 model"。
所以 `poetry-fallback` 只是**第二个可选模型**。选择方式: run 的 `context.model_name = "poetry-fallback"`(优先级: 请求 > agent config 的 `model` > 全局第一条,`agent.py:1050-1062`)。agent config 里**故意不写 `model`**,让请求能覆盖。是否做"primary 熔断后 worker 改用 fallback 重试"由 S3 决定;D4 说"不静默降级"针对的是 STUB,而不是换模型,但换模型应当在事件 `MODEL_USAGE.degraded=true` 里可见。
