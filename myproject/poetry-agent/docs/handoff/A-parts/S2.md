## 4. 偏差与决定记录

1. **文本版本 id**:真实是 `text-chun-wang-draft`(V002),契约 §3.3 示例的 `text-chun-wang-v1` 不存在于任何迁移。Mock 用真实 id。`gap-report.sql` 也引用了 `text-chun-wang-v1`,同样对不上。其他部分(S3/S4/S6)的夹具与示例需要对齐。
2. **注释数**:V004 实际带有 2 条注释(`ann-chun-wang-shanhe`、`ann-chun-wang-fenghuo`)。按任务要求默认 0 条;`MOCK_SEED_V004_ANNOTATIONS=1` 载入真实的两条。
3. **契约 §3.3 的 12 条 claim / 10 条 citation 无法由 V002+V004 复现**。全库与春望相关的是 13 条 claim、11 条 citation、4 个来源。不要在其他部分写死 12/10。
4. **claim 范围**:`snapshot` 严格照 Java(`subject_id = 作品`,春望仅 3 条,**看不到四层背景的 claim**)。`coverage`/`studio-view`/`works` 在 Mock 里放宽为"作品 + 其背景"(7 条),否则 Studio 无法渲染背景的史实/解释/演绎/未考状态。**这是 Mock 的自行决定**,S1 的 `studio-view` 是否同样放宽需对照;若 S1 只用 snapshot 的 claim 列表,Studio 会拿不到背景 claim。
5. **`MOCK_JSON_NAMING` 默认值**:按协调者通知由 `camel` 改为 `snake`(与真实 Java 一致);`camel` 仅用于模拟问题宿主以验证 BFF/worker 的兜底规范化。请求体恒同时接受两种键名。README 已说明。
6. **`locator_state`** 的占位判定是启发式(空→MISSING;以 `待`/`未核对`/`TBD` 开头→PLACEHOLDER;其余→SET)。Java 的 gap 只看 locator 非空,所以占位词 citation 在 gap 里仍算"有 locator",但在 studio 核验里不算 SET;这与契约 §3.2 一致,但两套口径并存。
7. **审计**:106 项审计不重算,固定 `audit_checks=106`、`audit_non_zero=[]`。
8. **`apply` 的 `Invalid` 渲染**:`CREATE_ANNOTATION` 的校验失败在 Java 里抛 `PoetryDraftService.Invalid`,由 `PoetryAuthoringAdvice` 渲染为 `{errno,data,error}` 的 400,不是 `AgentResponse`。Mock 照此还原。BFF/控制桥遇到这个形状要能容忍。
9. **Java 现状中值得 S1 注意的事实**(Mock 如实复刻,未擅自"修"):
   - `createAnnotation` 不校验 `version_id` 是否属于提案的作品,提案可以给别的作品的版本加注释;
   - `createProposal` 不检查 mandate 是否匹配作品(只 `INSERT IGNORE`),不匹配要到评审/应用时才暴露;
   - 提案读取走 `JOIN poetry_agent_run`,run 不存在则"proposal not found";
   - 重复 `review_id` 在 Java 是数据库唯一键异常(500),Mock 返回 500。
10. Mock 默认只绑 `127.0.0.1`。其他本机进程(MCP 的 `run()`、BFF 的 `run()`)是 `0.0.0.0`,这是它们自己的行为,未改。
11. 本机 `od` 命令被占用(会打印 `od` 的 CLI 用法),所以 `env-sync.sh` 里判断文件末尾换行改用 `tail -c 1` 加命令替换,不依赖 `od`。
12. 新增了两个契约未列的文件:`mock_store.py`(业务层)与 `scripts/content-agent/_dev-offline-common.sh`(三个启停脚本共用)。`dev-mock/` 下没有改动 `pyproject.toml`、`uv.lock`、根 `testpaths`。
