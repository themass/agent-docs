## 重放要回答什么

生产 voice.log 有两条 `voice turn timed out turn=… message_id=… mode=merged`
（120s 等不到 END 的 B 类回合）。修复后端侧不再静默（发 `error(empty_completion)`），
但「provider 为什么对那条请求返回空 completion」仍未证实——需要一次**有界**的
网关重放，看同一网关/模型对近似请求是否复现空返回（finish_reason 是什么）。

## 范围与条数（硬性）

- **恰好 3 次 LLM 请求**：2 条生产空回复回合的重建请求 + 1 条合成对照
  （正常应非空的已知请求，用来证明网关通路本身健康）。
- 每次请求 1 遍；**不自动重试**。唯一例外：请求在网络层失败（连接失败、未收到
  任何响应字节）时可重发该次，且总请求数封顶 4。

## 内容来源与脱敏

- 用户消息从生产 MySQL checkpoint 按那两条 turn 的 message_id 读出（只读 SELECT）。
  生产 QA `keep_content` 默认关——**当时那次 LLM 请求的逐字 prompt 没有留存**，
  重放是用当前代码的 prompt 装配器对 DB 消息重新组装（见「已知局限」）。
- 送出前脱敏：真实姓名/手机号/地址/标识符替换为占位符（`<姓名>` 等）；
  脱敏后的对话只存在于重放产物 JSONL，不进 git、不进 voice.log。
- 读取生产库属数据类操作：按现行口径可由会话执行（备份+回滚白名单前提），
  但重放本身仍需用户单独点头。

## 目标网关与数据保留

- 网关：生产 LLM 路由配置（`companion_llm_routing` / 104 `.env`）指向的
  同一网关与模型 id，直接 HTTPS chat-completions 调用。
- 执行位置：**建议 104 上跑**（密钥不出机；一条一次性 python 脚本，不属部署变更）。
  备选 Mac：需用户亲手提供密钥，用完即弃。
- 产物：一次运行的 JSONL（脱敏请求、响应全文、finish_reason、耗时）写在
  执行机操作员目录；B2 收口后删除。不落 MySQL/redis/事件流。

## 费用与请求数

≤3（+1 网络层重发）次请求，每次输入 ≤8k token、输出截 200 token。按生产
模型现价成本 < ¥1，可忽略；请求数与费用与条数同一封顶。

## 429 与停止条件

- 收到 **429 → 立即停止**，不排队不重试，回报协调人（现行 429 纪律）。
- 任何非预期形态（超时 >60s/次、5xx、响应解析失败）→ 该次即停，带原始
  HTTP 状态回报。
- 全局：wall-clock 10 分钟封顶；脚本单次运行只允许一个网关目标。

## 不会重复副作用——怎么确认

重放直连 completions 端点：**不经 turn_runner / 不写消息表 / 不推 redis /
不开 LiveKit 房间 / 不触发 TTS·STT / 不存任何消息**。provider 调用是无状态
推理，对用户数据零变更。确认后验：
1. 跑前跑后各一条 `SELECT COUNT(*)` 消息表——计数必须不变；
2. voice.log 无新增该 turn 相关行（重放不在 agent 进程内）；
3. redis 事件流 key 无新增（重放工具不 import turn 层）。

## 已知局限（先讲清再跑）

逐字原请求未留存（keep_content 关），重放证明的是「同网关+同模型+当前模板
对近似输入是否复现空 completion」，不是逐字复现。若要逐字取证：下次拨测窗
开 QA 同意（keep_content）留存后直接抓真请求——那条路线不需要重放。
