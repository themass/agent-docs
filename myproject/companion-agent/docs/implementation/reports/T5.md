# T5 报告：回合控制面

日期：2026-11-09。依据：D §6、A §5.1–5.3、P §3.1。

## 做了什么

1. **纯逻辑（domain）**：`domain/turn/queue.py` 的 `decide()`、`QUEUE_TRANSITIONS`、`DRAIN_BATCH_SIZE=10`、`DRAIN_MAX_ATTEMPTS=3`；`domain/turn/steer.py` 的 `SteerInbox`。
2. **端口**：`ports/turn_control.py` 的 `TurnControlPort`。app 层只依赖它，不 import adapters。
3. **Redis 适配器**：`adapters/cache/redis/control.py`
   - 键：`sess:{sid}:turn`、`sess:{sid}:lock`、`turn:{tid}:ctl`、`turn:{tid}:text`、`sess:{sid}:events`。
   - `_SUBMIT_LUA`：读锁与 phase，决定处置，并在同一脚本里 XADD 合并/插话消息（判定与投递原子）。控制消息带 `text`。
   - `_PHASE_LUA`：phase 只前进（none → pre_output → output/tool），不回退。
   - 锁：`SET NX PX 30000`，续租与释放均用 Lua 比较持有者后再操作。
   - 事件流：`publish` 用 `XADD MAXLEN ~5000`，30 分钟过期。
4. **应用层**：
   - `app/chat/submit.py`：幂等（`client_message_id`）→ `check_input` → 落库 → 原子判定 → STARTED 时取锁、初始化回合并启动，抢锁失败最多重判 3 次；抢锁反复失败则排队，不丢输入。
   - `app/chat/turn_runner.py`：续租（10 秒）、控制流读取（merge/steer/cancel）、phase 推进、增量合并（50 毫秒或 64 字符）、正文缓冲、收尾（落库助手消息、未注入插话转回队列、清 turn 状态、释放锁、尝试排空）。`merge` 只在未开始输出时生效；若与首 token 竞态，改为排队并发 `input.queued`。收尾只执行一次，失败也释放锁。
   - `app/chat/drain.py`：一批最多 10 条，`queued→draining` 认领（认领时 `drain_attempts` 已计数）；会话忙则放回；启动失败按 `DRAIN_MAX_ATTEMPTS` 置 `failed` 或回到 `queued`。

## 设计偏离 / 已知缺口

1. `send_cancel` 已实现但 HTTP 取消接口在 T6 才接线；`_attempt` 只在事件之间检查取消标志，无法打断一次正在等待的模型调用。T13 需要验证取消延迟，必要时在 `produce` 侧用 `aclose()` 强制中止。
2. 合并时 `turn_id` 下的用户消息没有被挂到该回合（`MessageStore.append` 在判定前已落库，`turn_id=None`）。合并文本已并入重跑的输入，但消息表中的 `turn_id` 需要 T13 补一次更新，或在 `MessageStore` 增加 `attach_turn`。
3. `produce` 由 bootstrap 注入。DeerFlow 适配器的 `stream()` 需要返回 `BrainEvent`（T4 已定义类型），接线放在 T6 之前完成。
4. Lua 脚本中动态键名（`turn:{tid}:ctl`）只在单节点 Redis 上安全。集群部署前要改为 `{sid}` 哈希标签（已写进 `control.py` 文档字符串）。
5. `read_text` 目前仅供首连快照使用，T6 实现。
