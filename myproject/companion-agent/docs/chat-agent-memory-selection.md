# 记忆后端选型

版本：草案 v1（2026-11-09）
状态：待决定。接口层（`MemoryPort` 与 `docs/chat-agent-memory-hooks.md` 的 hook 协议）已定，选型只决定端口背后的检索引擎，不影响调用方。

## 1. 约束

| 约束 | 来源 |
|---|---|
| 不下载模型，本地不跑 embedding 模型 | 用户明确否决（mem0 + 本地 bge-m3 路线已放弃） |
| 数据库是 MySQL 5.6，没有向量类型与向量索引 | 共享的 `vpn` 库，不能升级 |
| Redis 共享、TOS 已接入 | 运维已有，不新增基础设施优先 |
| 模型统一走 LiteLLM 网关 | `config/llm/routing.yaml`，目前只配了 chat 类模型 |
| 三种语言：中、英、阿拉伯语 | 产品要求 |
| 按应用隔离（`app:uid`），删除必须真删 | 设计 D §10、规范 §6 |

**未验证**：网关是否提供 embedding 模型、维度、价格、延迟。配置里没有任何 embedding 场景。验证方法是一次很小的 embeddings 调用，需要你批准使用线上网关。

## 2. 候选方案

### A. MySQL 词法检索（当前）

- 现状：`memory/recall.py` 的 CJK 单字与双字、其他语言按词；`memory/sql.py` 只在最近 500 条里排序。规范一致性检查已通过（内存、MySQL）。
- 优点：零新依赖，行为确定，可离线测试。
- 缺点：没有语义，同义词、换说法召回不到；只看最近 500 条，老记忆召回不到。
- 成本：无额外成本。

### B. 网关 embedding + MySQL 存向量 + 应用内余弦排序

- 写入时调网关 embedding，结果存为 `MEDIUMTEXT` 或 `BLOB`（float32，1024 维约 4 KB/条）。
- 检索：先用词法候选缩小范围（如前 100 条），再对候选做余弦重排。每用户条数有限时，全量扫描也可接受。
- 优点：不新增服务，完全落在现有 `MemoryPort` 实现里；调用方不变。
- 缺点：依赖网关 embedding 可用；每次写入、每次检索多一次网关调用（延迟与成本）；MySQL 5.6 无向量索引，条数大了要换引擎。
- 成本：embedding 调用费 + 每回合的检索延迟（待测）。

### C. Qdrant（自托管）+ 网关 embedding

- 优点：真正的近似最近邻；payload 过滤；每个应用一个 collection，与设计 D §10 一致；备份已在运维设计 O §11.2 里。
- 缺点：多一个要运维的服务；同样依赖网关 embedding。
- 说明：之前放弃 Qdrant 是因为 mem0 要本地模型，不是 Qdrant 本身需要下载模型。Qdrant 只存向量，embedding 仍然走网关。

### D. 托管向量服务（云厂商）

- 优点：不用运维。
- 缺点：要核实 API、数据驻留、价格；与 TOS 同厂商的话可以统一账单，但会增加厂商绑定。
- 状态：未调研，需要单独立项。

### E. mem0 + 本地模型

- 已否决：需要下载模型。不再考虑。

## 3. 比较

| | A 词法 | B 网关向量+MySQL | C Qdrant+网关 | D 托管 |
|---|---|---|---|---|
| 新增服务 | 无 | 无 | Qdrant | 厂商 |
| 语义召回 | 无 | 有 | 有 | 有 |
| 依赖网关 embedding | 否 | 是 | 是 | 视情况 |
| 中英阿兼容 | 词法有限 | 取决于 embedding 模型 | 同 B | 待测 |
| 规模上限 | 千级/用户以内 | 千级/用户（全扫描） | 十万级以上 | 厂商决定 |
| 删除真删 | 是 | 是 | 是（需验证） | 待验证 |
| 运维成本 | 低 | 低 | 中 | 低（有厂商成本） |
| 满足「无模型下载」 | 是 | 是 | 是 | 是 |

## 4. 建议

1. **现在**：保持 A。它已经通过一致性检查，是可用的基线。
2. **下一步**：先验证网关是否有 embedding 模型。如果有，实现 B，作为 `MemoryPort` 的另一个实现，用同一套一致性检查。
3. **规模或延迟不够时**：切到 C。因为接口层已定，切换只改组合根里的一行，调用方不变。
4. **D** 只在要用托管服务、且 C 的运维不可接受时再调研。

理由：B 不引入新服务，最贴近现有栈；C 是为规模准备的，现在上它是提前付运维成本。

## 5. 评测方法

选型不靠感觉，用同一套数据比：

- 评测集：约 30 组「记忆 + 查询」，中、英、阿各 10 组，包含同义改写、跨语言、长时间间隔的记忆。
- 指标：召回率@5（期望的记忆是否出现在前 5）、平均延迟、单次检索的网关调用次数。
- 对比对象：A、B（若网关可用）。C 只在规模测试里比。

评测集在实现前先写好，不根据结果调整。

## 6. 需要你决定的事

1. **是否批准一次网关 embeddings 调用**（约 10 个短句），用来确认网关是否提供 embedding 模型、维度与延迟。这是 B 的前提，也是唯一需要线上访问的步骤。
2. **每个用户预计多少条记忆**：决定 B 的全量扫描是否够用，还是直接上 C。
3. **每回合可接受的额外延迟**：决定检索是否可以异步，或只在召回阶段做向量重排。
