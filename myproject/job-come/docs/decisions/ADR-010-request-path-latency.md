# ADR-010：把请求路径上的外部往返去掉

- **状态**：已实现，待部署验证。
- **日期**：2026-11-14
- **前序**：ADR-009（checkpoint 每步写导致回合 16 秒）

## Context

ADR-009 解决了 agent 回合里的数据库往返。之后实测发现，同样的模式还在另外三处：

| 位置 | 实测代价 | 根因 |
|---|---|---|
| 认证 | **336 ms / 请求** | `GET` + `EXPIRE` 两次往返 |
| trace 账本 | 每事件一次 commit | 一个回合几十次往返 |
| LLM 审计 | 每次模型调用一次 commit | 在流循环里 `await`，挡住用户回复 |
| 指标 | `/metrics` 只反映 1/2 的 worker | 每进程独立 registry |

关键背景：**生产机和数据库/Redis 不在同一机房**。ping 169 ms、Redis 167 ms、
TCP 建连 183 ms。所以「多一次往返」不是小开销，它直接是用户感知的延迟。

AD-009 的教训在这里适用：每个数字都实测过，不靠推断。

## Decision

### 1. 认证：两次往返合成一次，再加本地缓存

`RedisSessionStore.get_and_touch` 用 `GETEX key EX ttl` 一次完成读和续期。
语义与 `GET` + `EXPIRE` 完全相同，成本减半。Redis < 6.2 无 `GETEX` 时回退到原路径。

`CachingSessionStore` 在其前面加 60 秒进程内缓存，把 Redis 从热路径上完全移除。

**为什么是 60 秒而不是 5 分钟**：缓存窗口等于「登出在另一个 worker 已经不生效」
的时长。5 分钟的窗口是安全问题，不是体验问题。真实的失效窗口是 `revoke` 的
pub/sub 广播延迟（毫秒级）；60 秒只是广播丢失时的兜底。

**为什么必须配 pub/sub**：`revoke` 删除本地、删除 Redis、再 `PUBLISH` 到
`<prefix>:revoked`。每个 worker 在 lifespan 里订阅并丢弃本地条目。没有这一步，
缓存就是一个倒计时中的安全漏洞。

**负缓存**：不存在的 session 也缓存。否则用过期 cookie 重放就能强制每个请求打
一次 Redis —— 那正是缓存要消除的负载。

### 2. trace 账本：一个回合一次事务

原来每个事件：锁 parent 行 + 查 tail + INSERT + commit ≈ 3 次往返 × 166 ms。
一个带工具调用的回合几十个事件，光账本就几秒。

改为：
- 事件在内存里攒成行（`_trace_row_for_stream_event` 只构行，不写库）
- 回合结束前 `append_batch` 一次分配 `seq`（仍是 parent 行的锁下分配，连续性不变）
- `confirm` / `error` / `done` 三类**仍然立即提交** —— 用户会去点、会去读的东西，
  不能因为断线而消失

**为什么不能纯异步**：客户端在 `done` 之后立刻拉历史。事件还在队列里没落库，
用户会看到一段历史凭空缺失。所以是「批量」不是「异步」，且 flush 必须在
`yield done` 之前。

### 3. LLM 审计：有界队列 + 后台写

审计行没有任何读路径依赖它，但原来在流循环里 `await record_call(...)`——
模型最后一 token 到用户看到回复之间，插了一次 166 ms 的数据库往返。

改为 `submit_call()` 入有界队列（默认 2000），后台任务串行写。
**满了就丢**，并每 100 条记一次警告：一个审计表撑爆队列把它本该解释的故障
变成了新故障；丢一行远好于卡住一个回合。

关闭时 `stop_audit_writer` 先 `queue.join()`（最多 5 秒）再取消，不丢在途行。

### 4. 指标：多 worker 合并

`enable_multiprocess(dir)` 让所有 worker 写同一个磁盘目录，由
`MultiProcessCollector` 汇总。为此指标定义从模块导入时创建改成首次使用时创建
（`_get(name)`），否则它们会在 `configure()` 之前就绑死默认 registry。

`/metrics/snapshot` 里带 `pid` 和 `host`：两个 worker 就是两个进程，面板隐藏这个
事实就等于只报了一半流量。

## 代价

- **trace 批量写**：回合中途崩溃会丢该回合未提交的历史行。业务数据（消息、
  确认）走独立事务，不受影响。
- **审计队列**：高负载下会丢审计行。这是有意的取舍，且有警告日志。
- **认证缓存**：worker 漏收广播时有最长 60 秒的登出延迟。

## 遗留

`/admin/metrics` 面板目前只有单进程视图。多 worker 合并需要在生产 `.env` 里
设 `JC_METRICS_MULTIPROCESS_DIR`，且该目录必须被 `prometheus_client` 独占。
未配置时面板会显示警告，不会假装数据完整。

## 教训

1. **跨机房部署下，「多一次 Redis 往返」就是 336 ms 的用户可感延迟。** 这类问题
   不会报错、不会告警，只会让人觉得「产品慢」。
2. **缓存必须配失效广播。** 否则它只是把一个问题换成了更危险的问题。
3. **批量 ≠ 异步。** 有读路径依赖的写入可以攒批，但不能脱离读的时序。
