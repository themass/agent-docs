# ADR-007：模拟面试由服务器状态机驱动，模型只生成窄的内容

- **状态**：Accepted（2026-11-09 用户同意重构方向；实施进度见下文）
- **日期**：2026-11-09

## Context

模拟面试（`coach-mock`）连续五轮真实验收没有通过。每轮都在修同一类问题：模型自己决定何时开场、何时登记主问题、何时追问、一条消息问几个问题、何时收尾。服务器只在事后检查（拒绝登记、改写回复、正则识别“你刚才说”、看门狗）。每修一条规则，模型就换一种方式违反另一条。

三个结构性缺陷：

1. **账本与候选人看到的话是两份数据。** `jc_mock_ask` 记录的题干与模型另写的回复各自独立，一致性只靠模型自觉。评分、覆盖率、题库都建立在账本上。
2. **评审没有标尺。** 同一档“强答”在两轮中分别是 6.9 和 3.8。校准集与分数漂移复核（`REMAINING-WORK` 第二节第 8、9 项）一直未做，达标线（6 分）因此不稳定。
3. **验收不可比。** 候选人由 Cursor 临场扮演，每轮回答不同，判分标准每轮重写，无法区分“代码变了”和“测试变了”。

另外，运行状态依附于进程：DeerFlow 线程的历史存在本机 SQLite 检查点里，停止信号是进程内的 `threading.Event`。当前是单机两个 worker，多机部署时两者都会失效（见 Consequences）。

## Decision

把面试流程的控制权从模型移到服务器。服务器用一个显式状态机决定下一步做什么；模型只在两个窄任务上被调用，并且输出结构化内容。

### 状态

```
WAIT_INTRO → ASKING_MAIN → (LISTENING) → FOLLOWUP? → ASKING_MAIN … → QA_OPEN → CLOSED
```

- `WAIT_INTRO`：开场已由服务器写出，等待候选人自我介绍。
- `ASKING_MAIN`：服务器从计划中按覆盖缺口选出下一道主问题，写入账本（同一事务），再渲染给候选人。
- `LISTENING`：候选人回答已记录，等待判定。
- `FOLLOWUP`：服务器按计数（每题最多 N 次追问）决定是否追问。
- `QA_OPEN`：候选人提问环节。
- `CLOSED`：收尾话术由服务器写出。

状态与当前题目存放在 MySQL（`mock_session.coverage` 已有雏形，实施时拆成独立列或表），不存放在 DeerFlow 线程里。

### 模型的两个调用（结构化输出）

1. **追问判定**：输入为当前主问题、候选人本次回答、本题已追问次数。输出 `{"followup": bool, "question": str | null, "quotes": [str]}`。服务器校验：`question` 必须只含一个问句；`quotes` 必须是候选人原话的子串，否则丢弃该追问。
2. **主问题口语化**：输入为服务器选定的题干与岗位要求标签。输出只改写措辞，不增删考点。服务器校验标签与考点关键词仍在输出中。

模型不再调用 `jc_mock_ask`、`jc_mock_open_qa`、`jc_mock_end` 来推进流程，这些工具改为服务器内部函数，不再暴露给模型。

### 候选人看到的消息

由服务器用结构化结果拼装：`[改写后的主问题]` 或 `[追问]`，再加固定的过渡语和收尾语。账本记录的题干就是候选人看到的题干，不存在两份数据。

### 上下文与多机

- 模型调用的上下文由服务器从 MySQL 账本组装：岗位、档案摘要、计划、本场已问的题与回答。不依赖 DeerFlow 线程历史。
- 因此会话可以被任何 worker 或机器接着处理，检查点不再是事实来源。
- 停止请求写入 `jc_agent_session.cancel_requested_at`（迁移 025，已实现），由运行方轮询。

### 评审与验收

- 评分细则改为有锚点的分档（每档写明典型表现），评审输出结构化分数与证据引用。
- 建校准集：每个级别的强、中、弱标准答案各若干份，人工定分。校准集作为回归测试，分数偏离超过 2 分标记为待复核（REMAINING-WORK 第二节第 8、9 项）。
- 验收改为固定剧本的候选人回放：同一脚本的输入在每轮完全相同，结果可直接比较。剧本与判定规则入库，不再由每轮临场决定。

### 保留与删除

- **保留**：题库（`jc_interview_question`）、覆盖率计算（`coverage.py`）、报告队列（024）、归档页、邮件、DeerFlow 运行时用于其他角色（非面试）。
- **删除（实施后）**：`mock_guard_service` 中为拦截模型行为而存在的规则（`parent_not_asked`、`followup_limit` 的部分分支、`refers_to_earlier_talk`）、`interview_reply.py` 的改写与正则、`_one_question_again`、`HOLDING_TEXT` 看门狗路径、`mock_opening` 中的 brief 注入。这些会在状态机通过验收后逐个删除，不与新代码同时存在。
- `coach-mock/SKILL.md` 大幅缩减：只保留人设与语气，流程规则由代码执行。

## Consequences

- **好处**：规则由代码强制，不依赖模型遵守；账本即事实；回放验收可比；多机只需共享 MySQL。
- **代价**：实施工作量大（预计先在一条分支上实现，并保留旧路径开关，通过验收后删除旧路径）；模型的口语化能力受限于两个窄任务的提示词质量，需要单独评估。
- **多机当前状态**：检查点仍是本机 SQLite（1 GB，无清理）。在状态机落地前，多机部署不安全；这一点由你决定是否在此之前引入 Postgres 检查点或粘性路由（已选择暂时保持现状）。
- **停止信号**：跨 worker 修复已实现（迁移 025，`run_once` 每秒轮询）。

## Implementation plan（分步，每步可独立验收）

1. ✅ 停止信号跨 worker（迁移 025、`cancel_run` 落库、`run_once` 轮询）。
2. ✅ 状态机接入：`jc/services/mock_flow.py`（纯决策与校验）、`jc/services/mock_interview_flow.py`（每回合编排，写账本，复用 `mock_guard_service` 的 ask/skip/open_qa/end）、`agent_service` 的分支由 `JC_MOCK_STATE_MACHINE` 控制，**默认关闭**。
3. ✅ 模型调用层：角色 `mock-flow`（`roles.yaml`，单次调用，技能 `agent/skills/public/mock-flow`）；追问判定与主问题改写都经过 `check_followup` / `check_phrasing`，不通过则用题库原文或不追问。
   - 候选人自己提问的回合（提问环节）仍由模型回答，旧路径不变。
   - 开启后面试官的 `coach-mock` 技能对面试回合不再生效。
4. 🟡 端到端验证（本地，真实模型）。环境：本地 MySQL 5.6（docker，迁移链到 025 通过）与 Redis，LLM 网关为服务器同一套配置；**没有连接生产库**。
   - 第一次跑暴露接线 bug：编排器收到的是被上下文包装过的文本，`下一题`、`结束` 失效。已修：在包装前保存候选人原文（`candidate_words`）。
   - 修后一场完整面试（脚本见 `/tmp/jc-e2e`，不入库）：开场、自我介绍、5 道主问题、追问、跳过、提问环节、结束，账本与对话一致，状态 `completed`。
   - 同一脚本关闭开关跑旧路径：账本仍是 `active`，而候选人已被告知面试结束；出现回指“你刚说的是……”；自我介绍后没有提问。
   - 未覆盖/未解决：候选人在提问环节的提问，走旧路径（DeerFlow）时，在本地两种开关下都超时，得到看门狗文本。生产库近 14 天只有 4 条此类回复，都在今天的测试轮次里，未查明原因。
   - 单次样本，未做统计；追问的相关性目前没有自动判定。
   - 未覆盖的接线：`agent_service` 中调用编排器的分支没有自动化测试，只靠这次端到端验证。
5. ⬜ 校准集与评分锚点，回归测试入库。
6. ⬜ 回放验收（固定剧本）替代临场扮演。
7. ⬜ 旧路径删除、`coach-mock` 提示词缩减（仅在 4 通过后）。
