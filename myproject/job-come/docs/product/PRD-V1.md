# PRD-V1：主动跳槽工作流闭环

- **状态**：已确认，V1 上线范围
- **最后更新**：2026-10-16
- **适用范围**：产品、设计、研发、测试、发布决策

## 1. 产品定位

JC 是服务于**主动跳槽、寻求职业提升的泛知识工作者**的 Web 产品。第一批用户聚焦互联网行业的全部知识工作岗位：研发、产品、设计、运营、市场、销售、客户成功、项目/交付、数据、HR、财务、法务等；不服务蓝领工人，也不将产品局限为研发岗位工具。

产品帮助用户把真实职业经历转化为可信、可修改、可用于面试表达的求职材料，并围绕目标岗位持续准备与复盘。成功标准不是生成一份文档，而是让用户以更清晰的职业叙事、更高质量的材料和更充分的准备主动冲击目标机会。

## 2. V1 用户与核心场景

| 用户 | 典型场景 | V1 必须解决的问题 |
|---|---|---|
| 有工作经历、准备换工作的互联网知识工作者 | 手中有旧简历、项目材料与目标 JD | 快速建档，保证事实可核对，再形成针对性简历 |
| 已有目标公司或目标岗位的用户 | 需要判断简历与岗位差距、准备面试 | 将 JD 转为岗位要求与差距分析，生成练习与复盘素材 |
| 已进入面试流程的用户 | 需要沉淀真实问题并迭代回答 | 保存面试记录、个人题库、回答和反馈，重复训练 |

### 产品原则

1. **事实优先**：原始经历、用户确认和 AI 建议必须可区分；不能把推断写成事实。
2. **用户最终确认**：模型不能自行确认档案变更；涉及事实的 patch 必须由用户明确确认。
3. **允许表达拔高，不允许虚构**：优化可提升表达强度，但必须能回到真实经历，并经得起模拟面试追问。
8. **不代投递**：不替用户提交申请、填写站点或发送消息。
5. **目标岗位驱动**：匹配分数用于诊断与建议，不得阻断简历修改或导出。
   同样地，**导出前质检也不得阻断导出**：它负责告知，不负责扣住用户的文件。
6. **数据归属隔离**：账号、档案、职位、会话、导出和面试记录必须进行归属校验。

## 3. V1 交付闭环

1. **建档：四个入口，一条解析与确认流程**

   | 入口 | 适用情形 | 实现 |
   |---|---|---|
   | 上传文件 | 手上有 PDF / Word / 图片简历 | `POST /profiles/upload` |
   | 粘贴文本 | 简历在聊天记录里，或宁愿直接打一段 | `POST /profiles/from-text` |
   | 和舟卡聊着写 | 没有简历，习惯边想边说 | 空档案 + `profile-interview` skill，由 agent 开口 |
   | 按问题逐项填写 | 没有简历，想要明确的问题清单 | `ProfileIntakePanel` + `build_intake_plan` |

   四个入口**汇入同一条管线**：粘贴的文本被写成 `.txt` source 交给上传那条解析链，
   因此解析状态、阶段上报、进度 UI、失败文案、语言识别、草稿待确认态都是同一套，
   不存在第二份实现。粘贴有 80 字下限——低于此结构器无可提取内容，
   会直接**编造一份档案**，拒绝比给用户一段他没干过的经历好。

   后两个入口是**两个按钮、两种体验**，不要再合并成一个：
   「聊着写」更自由，适合边想边说；「逐项填写」有明确清单，适合一次把该写的补齐。
   曾经只有一个按钮写着「用对话建一份简历」，点下去打开的是结构化问答表单——
   承诺了对话，交付了表单。

   逐项填写的问题由档案缺口算出（可证明终止、不重复、可断点续答），
   答案直接写入档案草稿并回显写入了哪些字段。
   进度存在档案里而非服务端会话，所以可以隔几天接着填。
2. **核对与确认**：用户编辑结构化档案；完成确认后，事实变更可追踪。
3. **简历优化**（步骤 3）：生成可审阅的优化版本和 `elevation_map`；每处改动标注所用的强化手段（补量化、加结果、强化主导性、明确对象、对齐岗位等），三档优化强度控制的是措辞离原文的距离，任何档位都不新增事实。
   同一步骤提供**证据补全**：系统按岗位族定位「本该有成果却没写出来」的要点，逐条向用户提问；
   用户填写的答案作为真实事实回填档案，下一次生成直接使用。
   「该写个数字」对很多人是空白题，所以缺成果类的问题下会给出**可点击的指标句式**
   （如 `P99 延迟：从 ___ms 降到 ___ms`），按目标岗位族给出这类岗位真正被衡量的维度。
   句式**只给维度、单位和留空符，永不预填数值**——填一个看似合理的数字会被直接采纳、
   送到真实招聘方，然后在面试里崩掉。
   同一步骤还提供**写作偏好**：显式切换目标岗位族，并选择最多 2 个**包装角度**
   （规模 / 主导 / 结果 / 深度 / 协作 / 岗位对齐）决定同一批事实先讲哪一面；不选则用岗位族推荐组合。
   角度只改呈现顺序与侧重，**不新增事实、不抬高动词强度**，也不放宽质检判定。
   页面同时显示**经历覆盖度**：源档案中被生成稿漏掉的要点会被点名列出，可一键重新生成。
   提示报的是**缺失条数**与被漏掉的原文摘录，并明确说出两个分支：
   想让面试官看到就重新生成，只是和别条说的同一件事就可以不管——
   只报 `已覆盖 / 总数` 会让用户分不清，然后无限重新生成。
   除了逐句改写，这一步还做**文档级重组**：为每段经历生成「负责范围」总述句（先总后分）、
   把摘要改为结论先行、把最强的证据提到段首、必要时把项目经历提到工作经历之前。
   重组**只重排不改写任何一句话**，并在界面上说明改了什么、为什么。
   同时展示**目标岗位的简历标准**（章节顺序、摘要公式、分量要求、这个岗位必须出现什么），
   以及本稿逐项是否达标与怎么改；未达标一律为建议，不阻断导出。
   我们**不以编造数字的方式让简历看起来更强**——理由与替代手段见
   [`../architecture/TECH-RESUME-WRITING.md`](../architecture/TECH-RESUME-WRITING.md) 第 3.6、11、12 节。
   注意这与「结构性提升」是两件事：排版、结构、分量不涉及新增事实，属于我们明确要做强的部分
   （见同文档第 16–17 节）。
   第 3 步的版面本身是产品约束：文档与控件**各自滚动**（一个滚动条推两列时，
   滚到左栏底部简历就被推出了自己的列），左栏问题获得焦点时右侧对应要点滚入视野并高亮。
   两列不做假对齐——内容不同、高度不同，强行对齐只能填空白。版面与字号由
   `scripts/verify_resume_steps.py` 量化断言，见
   [`../operations/QA-TESTING.md`](../operations/QA-TESTING.md) 版面量化门禁。
   第 3、4 步的主角是文档，所以**舟卡侧栏可以收起成一条 44px 的竖条**，文档因此多出
   400px；不用对话的用户不必为它让出三分之一屏。竖条上用一句话说明点开能做什么
   （首次未用过时有一次短促的提示动效），并在收起期间显示运行状态与未读回复数。
   **收起不等于结束**：正在跑的运行会继续跑完，回复照常到达，重新展开后在对话里。
   由 `scripts/verify_agent_rail.py` 断言。
4. **导出前质检与导出**（步骤 4）：独立页面。质检**只提示，不拦截**——
   导出 PDF、DOCX、HTML 三种格式始终可用，内容一致。
   - 质检**有发现**时，发现必须先被用户看见，确认一次（「我已了解，仍要下载」）即可下载；
     推荐位是「回到优化预览修改」，但不强制。
   - 质检**没跑起来或一直不返回**时（网关不可达、模型未开），照样能下载，
     并明确说明「这次没有完成检查，不影响下载」——这不是简历的问题，用户也修不了。
     转圈时提供「不等了，直接下载」。
   - 同时给出**投递前体检**（估算篇幅、要点条数与最长要点、岗位用词覆盖）和**经历覆盖度**复核；
     这两项一律为建议，并提供返回步骤 3 的入口。
   理由：一次模型调用不该成为核心交付物的单点故障，误判的代价全部落在用户身上。
   由 `scripts/verify_export_gate.py` 断言。
5. **JD 解析与匹配**：粘贴 JD 或在受限条件下读取公开职位页，得到职责、要求、来源和匹配/差距分析。
6. **模拟面试**：`warmup` 可不绑定 JD；`target` 必须绑定 JD。按一题一答保存答案、反馈和最佳答案。
7. **真实面试复盘**：记录公司、岗位、日期、轮次、问题与复盘，沉淀到个人题库后可继续练习。
8. **账户与安全**：注册、登录、邮箱验证、密码重置、会话管理与资源归属校验。

## 4. V1 页面与能力边界

| 页面/入口 | 用户结果 | 关键能力 |
|---|---|---|
| `/resume-agent` | 已确认档案、优化简历与导出物 | 上传解析**或对话建档**、三栏编辑、确认、证据补全、岗位族与包装角度选择、优化预览（强化手段 + 变更对比 + 经历覆盖度 + 文档级重组 + 岗位标准逐项检查）、Agent 对话、独立导出页（质检 + 投递前体检 + 覆盖度 + PDF/DOCX/HTML） |
| `/jobs` | 结构化 JD 与匹配报告 | 粘贴/受限读取、来源记录、差距分析 |
| `/interviews`、`/bank` | 可复用的练习与题库 | 模拟、答案、反馈、真实题归档 |
| `/applications`、`/campaign` | 自己维护的目标机会与节奏 | 申请漏斗和准备节奏，不代表自动代投 |
| `/settings/account`、`/auth/*` | 可管理的用户账户 | 个人配置、链接/4 位码邮箱验证、找回/修改密码、退出登录 |

## 5. 不属于 V1

以下三项是**下一个版本**的核心方向，不能出现在 V1 已交付或验收通过的表述中：

1. LiveKit 实时语音模拟面试；
2. 手机端体验；
3. 用户使用 Zoom 或腾讯会议进行真实面试时，实时听取面试官问题并提供答案建议。

上述第三项涉及隐私、授权、平台政策、实时性和安全边界；进入研发前必须完成单独的合规、安全与交互设计评审。

### 语音在 V1 能做到哪一步

V1 **有**语音输入，但**没有服务端语音识别**，这个边界要说清，免得被当成「语音功能已交付」。

| 环节 | V1 | 下个版本 |
|---|---|---|
| 录音 | 有（浏览器 MediaRecorder），原始音频进 TOS 长期留档 | — |
| 转文字 | 浏览器 Web Speech API | 服务端 STT，与 LiveKit 同批 |
| 模型读到的 | 浏览器转出来的文字 | 服务端转写（可支持任意浏览器与上传的音频文件） |

取舍理由：录音与留档的价值不依赖识别在哪做，而「用户口述一段经历 → 变成简历素材」
这条路靠浏览器识别已经能走通；服务端 STT 要同时解决模型选型、时长计费、
异步转写队列与隐私留存，和实时面试是同一批工程，放一起做更合理。

直接后果（**必须在 UI 上说清，不能只写在文档里**）：
Safari 与部分 Android 没有 `SpeechRecognition`，那里录音转不出文字，
本版本服务端也读不了音频。所以这些浏览器里麦克风按钮保持可见但禁用，
并提示换 Chrome/Edge 或直接打字 —— 让它悄悄消失会被当成页面坏了。

## 6. V1 发布判定

V1 的代码目标是一个可上线、可让首批用户完成全闭环的版本。发布必须同时满足：核心流程可用、真实依赖环境可连通、权限边界有效、导出质量通过、监控/备份/回滚已演练。具体门禁和当前状态以 [`../operations/QA-TESTING.md`](../operations/QA-TESTING.md) 为准。
