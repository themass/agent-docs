## 3. 你的任务：四个阶段

### Phase 1 — 稳定性（最容易发现问题）

**目的**：区分"偶发"和"必现"。我之前的用例大多只跑一次。

| # | 做什么 | 通过标准 |
|---|---|---|
| S1 | 全量 e2e 连跑 **3 次** | 3 次都是 62 绿；任何一次失败都记下来 |
| S2 | 单独把 `h-agent.spec.ts` 连跑 **5 次** | 5/5 绿。这是历史上最不稳定的路径 |
| S3 | 后端测试连跑 **3 次** | 失败数稳定在 7；若变动，说明有测试污染 |

**S2 是重点。** 如果 5 次里有 1 次失败，那是真实缺陷——记录下来，附完整 trace。

### Phase 2 — 语义正确性（我完全没测）

**目的**：接口 200 不等于内容对。这是最大的空白。

#### P2-1 简历生成的事实忠实度

1. 建档案，写入 **3 条可核对的硬事实**：
   - `把订单查询 P99 从 820ms 降到 130ms`
   - `日均请求 3000 万`
   - `管理 5 人团队`
2. 生成优化稿（三档都跑）
3. **逐字检查 HTML 输出**：
   - [ ] 三个数字都还在吗？
   - [ ] 有没有出现原文没有的**新数字**？（这是最严重的缺陷——编造数据会被投到真实公司）
   - [ ] 有没有出现原文没有的**新公司名/职位/时间**？
4. 对三档分别记录：哪些句子被强化了、强化手段标注是否与实际改动一致

> **这一条的价值高于前面所有测试。** 产品原则是"允许表达拔高，不允许虚构"，而虚构是模型最容易犯的错。

#### P2-2 覆盖度与岗位标准

- [ ] `coverage` 里点名的"漏掉要点"，去原文核对是否真的漏了（不能误报）
- [ ] `blueprint` 的达标项，去 HTML 核对是否真的达标（不能虚报）
- [ ] 故意删掉一条要点重新生成，覆盖度应该变

#### P2-3 模拟面试的评分与追问

1. 开一场 warmup，答 3 题（每题给明显不同的质量：好/中/差）
2. 结束后看报告：
   - [ ] 报告是否区分了这三题的质量？
   - [ ] 有没有给出具体改进建议，还是套话？
3. **故意答非所问**（问项目答天气），报告应该指出

#### P2-4 匹配分数的合理性

同一个档案，分别匹配：
- 完全对口的 JD（后端→后端）
- 完全不相关的 JD（后端→平面设计）

- [ ] 两者分数应有明显差异（>20 分）
- [ ] 分数接近说明打分是随机的

## 5. 你必须遵守的规则

1. **区分"测试写错"和"产品有问题"**——我今天在这上面错了 5 次。每次失败先看：
   - 请求字段名对吗？（我错把 `raw_text` 写成 `text`、`recommended` 写成 `recommendation`）
   - 挑的对象对吗？（我挑了 `message_count=0` 的 session 去测导出非空）
   - 等待条件对吗？（我在"生成中…"时就去断断言）
   **确认是产品问题再报。**

2. **不要为了让用例通过而放宽断言。** 要改断言，必须在报告里写理由。

3. **skip 要带原因，且要追问**：如果一个 skip **每次**都触发，那这个用例等于没写。我留下的 C-09b 就是这样——它跳过了 5 次我才发现是测试自己的问题。

4. **不要改生产 `.env`、不要重启生产服务、不要以 root 运行。**

5. **不确定就写 `UNVERIFIED` 并说明卡在哪**，不要猜。

6. **可以修 bug，但一次只改一处**，改完立刻跑对应用例，记录改前/改后证据。
