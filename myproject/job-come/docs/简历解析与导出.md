| 项 | 内容 |
|---|---|
| 版本 | **1.0** |
| 日期 | 2026-09-03 |
| 状态 | **M1 冻结候选** |
| 关联 | [技术方案.md](技术方案.md) · [MVP-产品方案.md](MVP-产品方案.md) §4.1 · [基础设施与LLM.md](基础设施与LLM.md) |

本文回答三件事：

1. **上传 PDF / Word / 图片（含扫描 PDF）后，如何识别用户信息？**
2. **PDF 与 Word 之间如何处理？**（结论：不做互转，只做单向管线）
3. **生成用户简历 PDF / Word 如何做？**

---

## 1. 设计原则（冻结）

| 原则 | 说明 |
|------|------|
| **Profile JSON 是唯一真相源** | 上传文件只用于「导入」；导出永远从 `jc_profile.payload` + `ResumeDraft` 重渲染 |
| **不做 PDF ↔ Word 互转** | 不从原文件改稿再转回；避免版式崩坏 |
| **分层解析、按需升级** | 能走便宜快路径就不调 OCR/VLM；扫描件/复杂版式才上多模态 |
| **Playwright 用于导出** | HTML 模板 → Chromium 打印 PDF，版式可控、与浏览器一致 |
| **多模态 LLM 用于理解** | 扫描 PDF、纯图片、复杂分栏时，页面图 + VLM 结构化抽取 |
| **LLM 一律经 LiteLLM** | 文本 `jobcome-fast`；视觉 `jobcome-vision`；业务代码不直连厂商 |
| **可复用进 agentkit** | 文档抽取、Playwright 渲染封装在 `libs/agentkit/adapters/`，JobCome 只编排 |

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                           导入（Ingest）                                 │
├─────────────────────────────────────────────────────────────────────────┤

│       ↓                                                                  │

│       ↓                                                                  │

│       ├─ Route B  复杂版式 / 表格        → Docling → MD                  │
│       └─ Route C  扫描 PDF / 图片 / A&B 失败 → 页图 + jobcome-vision     │
│       ↓                                                                  │

│       ↓                                                                  │
│  ProfileNormalizer（规则校验邮箱/手机/日期）                              │
│       ↓                                                                  │

└─────────────────────────────────────────────────────────────────────────┘

│                           导出（Export）                                 │
├─────────────────────────────────────────────────────────────────────────┤
│  Profile + ResumeDraft + templateId + locale + elevationLevel            │
│       ↓                                                                  │

│       ├─ Jinja2 → HTML（中一页 / 英两页模板）                             │

│       └─ docxtpl → DOCX      → TOS → jc_export_job                       │
└─────────────────────────────────────────────────────────────────────────┘
```

## 3. 问题一：如何识别用户信息？

### 3.1 不是「OCR 完就结束」

识别用户信息 = **文档理解 + 结构化映射到 `ProfilePayload`**，分三阶段：

| 阶段 | 组件 | 输入 → 输出 |
|------|------|-------------|
| **抽取** | `DocumentExtractor` | 原文件 → Markdown / 纯文本 / 页图 |
| **结构化** | `ProfileStructurer` | 文本或 VLM 结果 → `ProfilePayload` |
| **质检** | `ProfileNormalizer` | JSON → 带 `confidence` 的草稿 + 校验错误 |

MVP 要求（[MVP-产品方案.md](MVP-产品方案.md) US-1.1）：

- 3 份样本简历 ≥80% 核心字段正确
- 不确定字段标 `needs_review`，**不得静默写入已确认档案**

### 3.2 文件类型与路由

| 输入 | 检测 | 默认路由 | 升级条件 |
|------|------|----------|----------|
| **DOCX** | MIME + 魔数 | MarkItDown → MD | 文本框/复杂版式 → Docling |
| **文字型 PDF** | PyMuPDF 抽文本，字符密度 ≥ 阈值 | PyMuPDF → MD | 密度低、乱码、分栏错乱 → Route C |
| **扫描型 PDF** | 几乎无文字层 | **Route C（VLM）** | — |
| **PDF 内嵌大图** | Docling 版面分析 | Docling OCR 块 | OCR 置信度低 → Route C |
| **PNG / JPG** | MIME | **Route C（VLM）** | — |

**路由决策（伪代码）：**

```python
def choose_extract_route(file: SourceFile) -> Route:
    if file.is_image:
        return Route.VISION
    if file.is_docx:
        md = markitdown.convert(file)
        if md.quality_score >= THRESHOLD:
            return Route.MARKDOWN_ONLY
        return Route.DOCLING
    if file.is_pdf:
        text = pymupdf.extract_text(file)
        if text.char_density >= DENSITY_OK and text.reading_order_score >= ORDER_OK:
            return Route.MARKDOWN_ONLY
        if docling.can_ocr(file) and docling_preview_ok(file):
            return Route.DOCLING
        return Route.VISION
    raise UnsupportedFormat(...)
```

### 3.3 Route A/B：传统解析（便宜、快）

| 工具 | 用途 | 说明 |
|------|------|------|
| [PyMuPDF](https://github.com/pymupdf/PyMuPDF) | 文字 PDF 抽文本 | 毫秒级，M1 默认快路径 |
| [MarkItDown](https://github.com/microsoft/markitdown) | DOCX/PPTX 等 → MD | 微软维护，轻量 |
| [Docling](https://github.com/docling-project/docling) | 复杂 PDF/DOCX + OCR | 统一 `DoclingDocument`，表格/分栏 |

Route A/B 产出 **Markdown + 元数据**（页码、标题层级、表格 JSON），再交给文本 LLM 结构化。

### 3.4 Route C：多模态大模型（扫描件 / 复杂版式）

**何时启用：**

- 纯图片上传
- PDF 文字密度低于阈值
- Docling OCR 后置信度仍低
- 用户主动「重新识别（增强模式）」

**流程：**

```text
原文件
  → 按页渲染 PNG（PyMuPDF fitz 或 Playwright 打开 PDF 截图）
  → 最多 N 页（简历默认 N=3，可配置）
  → 调用 jobcome-vision（LiteLLM 多模态）
  → 严格 JSON Schema 输出 ProfilePayload
  → 与 Route A/B 结果 merge（VLM 优先覆盖冲突字段，并标 confidence）
```

**VLM Prompt 要点：**

- 只抽取简历上**明确出现**的信息；推测必须标 `inferred`
- 经历/教育/技能分条；日期统一 `YYYY-MM` 或 `YYYY`
- 输出必须符合 `ProfilePayload` Pydantic schema（`response_format: json_schema`）

**页图渲染：**

| 方式 | 场景 |
|------|------|
| PyMuPDF `page.get_pixmap()` | Worker 内默认，无浏览器依赖 |
| Playwright `page.pdf()` 的反向：打开 file:// PDF 截图 | 需要与导出共用 Chromium 时 |

M1 建议：**ingest 用 PyMuPDF 渲页，export 用 Playwright**，职责分离。

### 3.5 文本结构化：`jobcome-fast`

Markdown 或 Docling 文本 → `ProfileStructurer`：

```text
输入：markdown + 可选 tables_json
模型：jobcome-fast（DeepSeek / 便宜文本模型）
输出：ProfilePayload JSON
后处理：ProfileNormalizer 正则校验 email/phone；矛盾日期标 needs_review
```

**不**把全文简历写入 Langfuse trace（PII）；只记 `profile_id`、字段 path、hash（见 [可观测性与Trace.md](可观测性与Trace.md)）。

### 3.6 数据落库

| 表 / 字段 | 内容 |
|-----------|------|
| `jc_profile_source` | 原文件 OSS key、`parse_status`、`parse_error` |
| `jc_profile.payload` | 结构化 JSON |
| `jc_profile.contact_name` | 从 payload 反规范化，便于列表展示 |
| `confidence` | 字段级，存在 payload 各 experience/education 内 |

异步任务：`ProfileIngestService.ingest(source_id)`，目标 **< 60s**（MVP）。

## 4. 问题二：PDF 与 Word 互转？

### 4.1 结论

| 方向 | 做不做 | 说明 |
|------|--------|------|
| 上传文件 → Profile | ✅ | Ingest 流水线 |
| Profile → PDF | ✅ | Playwright 渲染 |
| Profile → DOCX | ✅ | docxtpl 模板 |
| PDF → DOCX / DOCX → PDF | ❌ | 不做对用户暴露的互转 |

### 4.2 内部中间表示（Resume IR）

```text
ProfilePayload
  + ResumeDraft.sections（拔高后段落）
  + elevation_map
  + template_id（zh-one-page / en-two-page）
  + locale
        ↓
  ResumeRenderContext（内存对象，不落库）
        ├─→ HTML（Jinja2）
        └─→ DOCX（docxtpl 同一套字段）
```

## 5. 问题三：如何生成 PDF？

### 5.1 主路径：HTML + Playwright（冻结）

```text
ResumeRenderContext
  → Jinja2 渲染 HTML（内联 CSS，A4 @page）
  → Playwright Chromium: page.set_content(html); page.pdf(...)
  → 上传 OSS
  → jc_export_job.status = done, storage_key = ...
```

**为什么用 Playwright 而不是 WeasyPrint：**

| 项 | Playwright | WeasyPrint |
|----|------------|------------|
| 版式与浏览器一致 | ✅ | 部分 CSS 差异 |
| 中文简历、分页控制 | ✅ 成熟 | 需更多调 CSS |
| 团队可本地预览 | 同一 HTML 浏览器打开即所见 | 需单独看 PDF |
| 运维 | Worker 装 Chromium（Docker 官方镜像） | 轻量 |

WeasyPrint 保留为 **无 Chromium 环境的开发备选**，生产以 Playwright 为准。

### 5.2 Word 导出：docxtpl

- 模板文件：`jobcome/templates/resume/zh-one-page.docx`（占位符 `{{ contact.name }}` 等）
- 与 PDF 共用 `ResumeRenderContext` 字段
- 不走「HTML 转 docx」

### 5.3 模板与版式

| template_id | locale | PDF 页数 |
|-------------|--------|----------|
| `zh-one-page` | zh-CN | 1 页 A4 |
| `en-two-page` | en | 2 页 A4 |

导出记录绑定：`profile_version` + `elevation_level` + `template_id`（`jc_resume_draft` / `jc_export_job`）。

### 5.4 导出前 Reviewer 闸门

`ResumeReviewer`（规则 + 可选 `jobcome-fast`）：

- 无假公司 / 假学历 / 假项目
- 拔高句可关联 `elevation_map` 证据
- 未通过 → 阻断导出或用户确认风险

**不经 DeerFlow**；在 `ResumeService.export()` 内同步执行。

## 6. LLM 模型别名（LiteLLM）

应用与 Worker **只认逻辑名**：

| 别名 | 用途 | 建议后端（可轮换） |
|------|------|-------------------|
| `jobcome-fast` | MD→JSON、JD 解析、Reviewer 文案 | `deepseek/deepseek-chat` |
| `jobcome-writer` | 拔高、改稿（DeerFlow） | `deepseek/deepseek-chat` 或 `gpt-4o-mini` |
| `jobcome-coach` | 面试辅导 | 同上 |
| **`jobcome-vision`** | **简历页图 OCR / 扫描 PDF** | **`qwen-vl-ocr`**（`YUAI_VISION_*` 独立配置） |

配置示例见 [deploy/litellm/config.example.yaml](../deploy/litellm/config.example.yaml)。

**成本控制：**

- VLM 仅 Route C；每份简历默认 ≤3 页图
- 访客 ingest 按 `guest_session` + IP 限流
- LiteLLM 可对 `jobcome-vision` 设 `max_budget` / 日配额

## 7. 开源项目选用表

### 7.1 导入

| 项目 | 角色 | 采用 |
|------|------|------|
| [docling](https://github.com/docling-project/docling) | 复杂文档 + OCR | ✅ Route B |
| [markitdown](https://github.com/microsoft/markitdown) | 快速 MD 转换 | ✅ Route A |
| [PyMuPDF](https://github.com/pymupdf/PyMuPDF) | 文字 PDF + 页图渲染 | ✅ 必选 |
| [marker](https://github.com/VikParuchuri/marker) | 高质量 PDF→MD | ⚪ 备选（重、要 GPU） |
| [unstructured](https://github.com/Unstructured-IO/unstructured) | 元素级解析 | ⚪ 备选 |
| [PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR) | 中文 OCR | ⚪ Docling 不够时 |

### 7.2 导出

| 项目 | 角色 | 采用 |
|------|------|------|
| [playwright-python](https://github.com/microsoft/playwright-python) | HTML → PDF | ✅ **生产主路径** |
| [docxtpl](https://github.com/elapoulet/python-docx-template) | Word 模板 | ✅ |
| [WeasyPrint](https://github.com/Kozea/WeasyPrint) | HTML → PDF | ⚪ 开发备选 |
| [pandoc](https://github.com/jgm/pandoc) | 万能转换 | ❌ 不上主路径 |

### 7.3 不建议

- 直接套用第三方 `resume-parser` 库（字段模型与 `ProfilePayload` 难对齐）
- 让用户下载「转换后的 Word」再编辑（违背 Profile 真相源）

## 8. 代码落位（与工程规范一致）

```text
libs/agentkit/adapters/
  document/
    extractor.py          # Docling / MarkItDown / PyMuPDF 封装
    page_renderer.py        # PDF/图片 → PNG bytes
  llm/
    structured.py           # OpenAI-compat chat + json_schema
    vision.py               # 多模态 messages（image_url + text）
  render/
    playwright_pdf.py       # HTML → PDF bytes

job-come/src/jobcome/
  services/
    profile_ingest_service.py
    profile_structurer.py
    resume_render_engine.py
    resume_reviewer.py
  workers/
    ingest_worker.py        # ARQ: parse_profile_source
    export_worker.py        # ARQ: render_export_job
  templates/
    resume/
      zh-one-page.html
      en-two-page.html
      zh-one-page.docx      # docxtpl
```

**禁止**在 `jobcome/services/` 里直接 `import docling`；一律经 agentkit adapter。

## 9. API 与状态机

| API | 说明 |
|-----|------|
| `POST /profiles/upload` | multipart → OSS + 创建 `ProfileSource` + 入队 ingest |
| `GET /profiles/{id}` | 含 `parse_status`、payload 草稿 |
| `POST /profiles/{id}/confirm` | 用户核对后冻结版本 |
| `POST /profiles/{id}/export` | 创建 `ExportJob`，异步渲染 |
| `GET /exports/{id}` | 轮询状态；`done` 时返回签名 URL |

**parse_status：** `pending` → `processing` → `done` | `failed`

**export status：** `pending` → `processing` → `done` | `failed`

## 10. 部署与 Worker

```text
jobcome-api          FastAPI（上传、查询、入队）
jobcome-worker       ARQ + Playwright Chromium + Docling（CPU）
litellm              :4000（jobcome-fast / jobcome-vision）
```

Docker：`mcr.microsoft.com/playwright/python:v1.49.0-jammy` 作为 worker 基础镜像。

本机开发：

```bash
# API
uv run uvicorn jobcome.main:app --reload

# Worker（另终端）
uv run arq jobcome.workers.settings.WorkerSettings

# LiteLLM（配好 jobcome-vision 的厂商 Key）
litellm --config deploy/litellm/config.yaml --port 4000
```

## 12. 风险与对策

| 风险 | 对策 |
|------|------|
| VLM 成本高 | 路由阈值 + 页数上限 + 仅失败时升级 |
| VLM 幻觉（假经历） | `confidence` + 核对页 + Reviewer 阻断 |
| Playwright 内存 | Worker 并发限制；浏览器复用单例 |
| 解析超时 | 60s 超时 → `failed` + 可重试「增强模式」 |
| PII 日志 | trace 只记 id/hash，不落全文 |
