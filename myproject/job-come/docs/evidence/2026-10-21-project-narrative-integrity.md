# 项目叙事被拆散：根因、修复与边界

## 可复现根因

1. 文本解析提示词明确要求把复合 accomplishment 按分号、句子边界拆成多个 highlights。OCR 提示词也要求拆出多个结果。
2. `ResumeElevator._split_bullet` 再次按 `[；;\n]+` 拆分模型输出，破坏完整项目段落。
3. `compose_document` 对同一项目的每条陈述按证据强度排序，能把成果移动到背景/实施之前。
4. writer 的 method/structure/targeting/family-backend、blueprint 存在拆分凑数量、按量化强度重排的指令，reviewer 则错误地假设系统应当这样排序。

复现使用合成样本，不使用真实个人数据或付费模型。新增测试在修复前实际失败，包含分号拆分、背景/行动/成果顺序以及生产 writer 流程。

## 修复

- 文本/OCR 解析规则改为保留原始语义项目/段落单元，不以标点或视觉换行确定拆条边界。原本独立的子条目仍留在同一项目下，不要求一个项目永远只有一条。
- 移除标点拆分和代码层段内强弱排序；章节顺序调整仍保留。
- writer 的各层提示词与 reviewer 约束对齐。要求保留实体 ID、源段落数量、归属与顺序，取消最低条数/长度驱动的拆条建议。数量只作为完整性参考。
- 生产 writer 新增 `_preserve_source_units`：按 ID 或唯一旧式名称匹配实体；项目/任职数量、单元数量不一致或实体对应不明确时，回退到对应原文块。没有再次调用 LLM，没有写回 profile，也没有猜测如何合并。
- 回退情况写入 `generation.mode=structure_guarded` 与 warning，利用已有预览提示展示，不伪装为全部优化成功。
