# 上传解析：基于文档证据的单策略流水线

## 问题与约束

本地日志显示：原生文字结构化请求超时后又进行了 Markdown 结构化，随后进行 PDF 视觉结构化，累计接近 7 分钟。服务不可用被误判为文档质量差，是首要根因。不能仅通过提高等待时间、假进度或少解析内容来“提速”。

## 设计模式与职责

采用 **Pipeline + Policy/Strategy Selection**，不增加框架、策略工厂或数据库表。

```text
ProfileService                 权限、来源、对象存储、状态与档案持久化
    ↓
ProfileIngestService            有界流水线编排、阶段回调、统一终止
    ├─ DocumentExtractor       原生文字、本地备用转换、PDF 扫描页检测
    ├─ ingest_plan             纯函数：文档证据 → 不可变 IngestPlan
    ├─ ProfileStructurer       文本 → ProfilePayload
    └─ ProfileVisionExtractor  图片/扫描 PDF → ProfilePayload
            ↓
        LLMRouter              唯一模型 failover/JSON 验证/审计边界
```

选择路线后只执行该路线。不存在“模型失败 → 换文档格式再次结构化 → OCR”的跨路线重试。结构化字段少只产生待核对草稿，不证明原生文字提取失败。

## 路由

| 文档证据 | 策略 |
| --- | --- |
| 原生文字可读 | 单次文本结构化，不因普通头像/Logo 追加 OCR |
| 本地文字不足，尚无扫描页证据 | 本地 Markdown 备用提取，再选择一次策略 |
| PDF 扫描/混合页面 | 整份 PDF 视觉结构化，不先花费一次文本模型请求 |
| 图片 | 视觉结构化 |
| DOCX 无可读文字但有内嵌图片 | 内嵌图视觉结构化 |
| 模型/网关/JSON 处理失败 | 当前任务失败，不换文档路线重试 |

`usable_text` 是保守的可读性信号（至少 40 个字母/数字/汉字且替换字符比例低于 2%），不是经历完整性的评分。PDF 页面检查使用“文字稀少 + 图片面积至少半页”的启发式。它不是完美的文档分类器。

## 性能和终止

- 解析流水线默认总预算 120 秒，含本地提取和模型 fallback。
- 文本/视觉请求单次预算默认 25 秒；SDK 内部重试仍受流水线总预算限制。
- 持久化编排外层保留额外 30 秒保护窗口；存储读取单独最多 30 秒。
- 原生提取、页面检查、PDF 渲染、对象读取移到线程，避免阻塞事件循环和状态轮询。
- 超时/取消停止异步调用并向上返回；取消不能强杀已经开始的原生工作线程。需要进程级隔离的恶意文档处理不是本次实现。
- 模型失败不覆盖旧档案，来源落 `failed`，公开错误不包含供应商响应。
- 保留既有 `mock_fallback` 的“LLM 显式关闭/旧 .doc”兼容分支；不将它宣称为生产模型解析成功。

## 前端

解析中的来源维持“上传解析”，后续步骤不可进入；工具栏不显示确认/预览操作。阶段文案区分本地备用提取、扫描识别、文本结构化，保留真实耗时，不估算虚假百分比。删除面向终端用户的后端日志排查指令和“复杂文档多轮解析需数分钟”的兜底文案。

## 内容保护与边界

- 视觉解析此前只取前 5 页；生产视觉路径现要求所有页面均能纳入，否则明确拒绝，不再静默漏掉后续页面。
- 文本结构化移除额外的 30,000 字符截断；仍沿用上传/提取器原有大小上限。
- 混合 PDF 目前整份视觉处理，尚未做逐页 OCR 合并；DOCX 的混合文字/扫描片段也不是完整的版面理解系统。
- 未引入解析结果跨上传缓存、分布式队列/任务租约、同文件去重和无重新上传的重试接口。不把这些未实现能力写成已完成。

## 验证

- 后端解析、计划、真实本地 PDF 检查、持久化失败生命周期与提取器聚焦测试：61 passed；PyMuPDF 5 条依赖弃用警告。
- 前端 Node 测试：36 passed（含解析期间不渲染旧档案/预览的 React 服务端渲染回归）。
- Next 生产构建、类型检查通过。
- Ruff 聚焦文件检查通过。
- 未使用真实付费模型、未执行迁移或修改业务数据库；未做该用户文件的真实模型性能评测，因此不能承诺具体完成秒数或所有异常 PDF 都能正确解析。
