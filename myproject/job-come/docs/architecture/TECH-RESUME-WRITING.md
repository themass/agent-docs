# TECH-RESUME-WRITING：简历优化方法论与实现约束

- **状态**：已确认的 V1 实现约定
- **最后更新**：2026-10-16

本文档回答一个产品问题和一个工程问题：**我们凭什么说简历被"优化"了**，以及**这套方法在代码里由谁保证**。
措辞与档位定义是产品契约，改动前先读第 5 节的信任边界。

## 1. 为什么需要写下方法论

一个"让简历更好"的按钮如果没有可说明的方法，会产生两类失败：

- 用户不知道系统做了什么，无从判断是否该接受改写，产品被当成随机换词器。
- 模型倾向于写出自信但无据的句子。漂亮的假 bullet 比平庸的真 bullet 危险得多——它在面试追问时崩塌，代价由用户承担。

所以方法论必须同时是**写作指令**和**可核验的约束**。

### 1.1 本文结论的来源与置信度

本文此前把所有结论都写成「业界共识」，这不诚实。实际来源分三档，下文结论凡与此表冲突者以此表为准：

| 置信度 | 哪些结论 | 来源 |
|---|---|---|
| **有公开出处** | XYZ 公式（Accomplished X as measured by Y by doing Z） | Laszlo Bock（前 Google SVP of People Ops）公开建议 |
| **我们的推理** | 动词强度分级、量化阶梯的四级排序、覆盖度硬约束、岗位族 playbook 的内容 | 由「可核验性」这一条原则推导：越具体的表述越容易被证实或证伪，所以按可核验性排序。**没有实验数据支持具体排序** |
| **未验证假设** | 「最近一份工作的第一条 bullet 被读最多」 | 符合直觉与常见建议，我们**没有核实过**。标为假设 |
| **常被误引，不作依据** | 「招聘方只花 6 秒扫一份简历」 | 源自 Ladders 眼动研究，样本小且场景特定。我们不拿它当设计依据，篇幅结论改用自测数据（见 6.4） |

写作、审稿、诊断三处的具体阈值若需调整，应当优先补测量，而不是继续加推理。

## 2. 核心写法：Action + Object + Outcome

每条经历要点按"动作 + 对象 + 结果"组织，即 XYZ 公式按中英文最自然的阅读顺序表述。

| 成分 | 含义 | 缺失时 |
|---|---|---|
| Action | 具体动词，体现做了什么 | 不可接受 |
| Object | 动作作用的系统、产品、团队、流程或指标 | **永不可接受** |
| Outcome | 由此发生的变化，源数据支持时量化 | 可接受（源数据确实没有结果时） |

- 差：`深入研究分布式系统，主导相关优化工作。`（无对象、无结果、无法核验）
- 好：`主导看点快报后台从 PHP 单体迁移到 tRPC-Go 微服务，解决发布耗时与资源损耗问题，成本优化 20%。`

缺 Outcome 时写准 Action + Object 即止，**不得补一个编造的数字**。

## 3. 三条强化维度

### 3.1 动词强度分级

选择**证据支持的最强动词**，不得越级。

| 级别 | 中文 | 英文 |
|---|---|---|
| Ownership | 主导 / 负责 / 搭建 / 设计并实现 / 从 0 到 1 落地 | own, lead, architect, build, launch |
| Improvement | 重构 / 优化 / 治理 / 收敛 / 提升 | refactor, optimize, reduce, scale |
| Collaboration | 推动 / 协同 / 牵头 | drive, partner, coordinate |
| 弱（禁作主动词） | 参与 / 协助 / 了解 / 熟悉 / 接触 | involved in, helped with, familiar with |

原文写 `参与` 时不得改写为 `主导`。这是硬约束，不是风格偏好。

### 3.2 量化阶梯

取源数据支持的最高一级，不得虚构更高一级：

1. 直接指标：`成本优化 20%`、`Lead Time 25 天 → 8 天`
2. 规模量级：`全量推送 4kw`、`服务 6 条业务线`、`管理 8 人团队`
3. 定性结果：`支撑跨业务一致性事务`、`解决模块耦合`
4. 无结果：只写精确的 Action + Object

前后对比（`从 25 天缩短至 8 天`）优于裸百分比，因为它同时给出了基线。

### 3.3 经历内排序

把**ownership 最高、成果最可验证**的一条放每段经历首位，其余递减。

依据是一个**未验证假设**：最近一份工作的第一条 bullet 被读到的概率最高。这符合直觉，但我们没有核实过。
即使假设不成立，「最强的放最前」也不会比随机顺序更差，所以照此执行；但不要把它当成已验证的事实对用户陈述。

### 3.4 覆盖度：篇幅必须匹配职业长度

**写少了比写过比写夸张更常见，也更致命。** 资深候选人的简历被压成几条短 bullet，读者不会理解成「简洁」，
只会理解成「这人没干过什么」——没写在纸上的 scope 读者无法推断。

硬约束：

1. **源档案里每一条 `highlights` 都必须被覆盖。** 可以改写、合并、拆分、重排，不得为了短而丢弃成果。
2. **`projects` 非空时必须渲染 `project_blocks`。** 这是独立 section，模板和导出都支持。
   档案有项目但 `project_blocks` 为空是缺陷，不是风格选择。项目按**与经历相同的密度**书写：
   每条 `highlights` 一个 bullet，不是压缩成一行概述。模型若漏掉 `project_blocks`，
   `ResumeElevator` 会用确定性 builder 的结果回填，避免真实工作被模型静默删除。
3. bullet 数量跟着证据走，不是跟着固定目标走。多年资深岗配 3 条、而一年短岗也配 3 条，是错的。
4. 只有当两条源要点描述**同一件事**时才允许合并。不同系统、不同成果、不同时间段必须分开。
5. 源档案确实单薄时简历就该短——但**绝不能用编造的 scope 去填**。源文单薄和被丢弃在纸面上
   长得一模一样，所以永远不要制造第二种情况。

bullet 数量**没有上限**。3 是单薄岗位的下限；源文有 11 条要点的多年资深岗就写 11 条。

> **历史缺陷（已修）**：`resume_elevator._trim_bullets` 曾把 LLM 路径每段经历硬截到 8 条。
> 这与「抽取无损」直接矛盾——抽取被要求一条不丢，渲染却静默删掉第 9 条起的所有内容。
> 现已替换为 `_clean_bullets`：只去空行与完全重复项，不限条数。篇幅是写作 prompt 的职责，
> 不是解析层该做的裁剪。

### 3.5 抽取环节是无损的

`profile_structurer.md` / `profile_vision.md` 产出的是**全链路唯一事实来源**。下游写作模型能改写它捕获的内容，
但**无法恢复它丢掉的内容**——抽取时漏掉的东西在用户简历里就是彻底消失了。

所以抽取环节的指令和写作环节相反：**只管全，不管精。**

- 不许概括、不许合并、不许"挑最好的几条"。源文 9 条要点就是 9 条 `highlights`。
- 一条要点打包多个成果（`负责 A，同时搭建 B，推动 C 上线`）必须拆成多条。
- 数字、单位、百分比、QPS、人数、业务线数、系统名、前后对比（`25 天 → 8 天`）必须原样保留。
  丢掉 `4kw` 或 `120+ 服务` 等于摧毁整份简历赖以成立的证据。
- `项目经历` 是会被渲染的真实 section，不是边角料的堆放处。
- **项目的成果写进 `projects[].highlights`，一条一个，与 `experiences[].highlights` 同规格。**
  `description` 只是「这个项目是什么」的一行概述，不是成果段落。源文列了 6 条项目要点就是 6 条
  `highlights`，合并成一段 `description` 等于丢掉 5 条。

### 3.6 「可以夸张」的处理方式（重要产品决策）

需求原话是「简历要丰富不要少精，我们是可以夸张的」。**丰富这一半完全采纳**（见 3.4 覆盖度），
**夸张这一半不按字面实现**。理由两条，且第二条是硬的：

1. **代价全部落在用户身上。** 编造的指标能过筛，但在面试被追问时崩塌，而那一刻我们不在场。
   一份撑不住追问的简历，比一份平实的简历更糟——后者只是没拿到机会，前者是当面失信。
2. **放开它会让整套核验失效。** 审稿器把「无源支撑的事实」判为最高级别发现（见 6.3）。
   如果写作侧被允许夸张，审稿侧就必须同时放宽，那么所有核验都变成装饰。两者不能并存。
   （审稿的发现不阻断导出，见 6.3.1——但那是「谁来决定」的问题，不是「还查不查」的问题。）

但「拒绝夸张」不等于交付一份干瘪的简历。真实诉求是**让面试官有兴趣**，这个诉求我们用一组替代手段满足，
它们比夸张更有效且不冒风险：

| 诉求 | 替代手段 | 实现 |
|---|---|---|
| 内容太少，撑不起资历 | 覆盖度硬约束：源文每条要点都必须落到纸面，bullet 数不设上限 | 3.4、`_clean_bullets` |
| 做过的事看起来不起眼 | 按岗位族换一套表述角度，用这个受众真正在读的词汇描述同一件事 | 第 8 节 `role_families.py` |
| 成果写不出来 | **定位本该有成果却缺失的要点，逐条向用户提问**，答案作为真实事实回填 | 第 9 节 `evidence_gaps.py` |
| 同一段经历想换个讲法 | **包装角度可由用户选择**：同一批事实换先讲哪一个 | 第 11 节 `framing_presets.py` |
| 生成稿比真实经历单薄 | **覆盖度审计**：逐条比对源文要点是否仍在纸面，掉了就点名 | 第 12 节 `resume_coverage.py` |
| 内容对但读起来没分量 | **文档级重组**：范围句、结论先行的摘要、最强证据提到段首、节序调整。**一句话都不改** | 第 16 节 `resume_structure.py` |
| 不知道这类岗位该怎么写 | **岗位 blueprint**：同一套标准写给模型、测生成稿、给用户看 | 第 17 节 `resume_blueprint.py` |
| 根本没有简历可改 | **对话建档**：从零把经历问出来 | 第 18 节 `profile_intake.py` |
| 知道该写数字，但不知道写哪个 | **指标候选句式**：按岗位族给出「维度 + 单位 + 留空句式」，点一下填进输入框 | 3.6.1、`metric_prompts.py` |

第三条是关键认知：**大多数简历弱，不是因为经历弱，而是因为最强的证据从没被写下来。**
用户知道那个数字，只是没有人问过他。所以正确的产品动作是**问**，不是**编**。

倒数三条划出另一条界线，同样重要：**「这份简历读起来没分量」与「这份简历缺事实」是两个不同的问题。**
前者的解法是结构（第 16–17 节），后者的解法是提问（第 9、18 节）。
用本节「不编造」的理由去挡结构性提升的诉求是**误用**——重排与范围句不新增任何事实。

这条立场是产品契约。若要推翻它，必须同时改写审稿器的严重级别定义，并明确告知用户其承担的风险。

#### 3.6.1 指标候选项：只给维度，永不给数值

「让用户自己想一个数字」对很多人是个空白题——他知道自己做过什么，但不知道这类岗位
**该用哪个维度**衡量。所以证据补全的问题下面会挂一排可点击的候选句式：

```
P99 延迟：从 ___ms 降到 ___ms     （越低越好）
QPS：从 ___ 提升到 ___            （量级）
```

**不可违背的契约：候选项永不携带数值，连「看起来像值」的占位符也不行。** 只给维度、单位和
留空的句式。理由就是本节第 1 条：预填一个看似合理的数字，用户会直接接受、送到真实招聘方、
然后在面试里崩掉，代价全在他身上。给句式是降低表达成本，给数字是代替他编。

实现要点（`services/metric_prompts.py`）：

- 候选项从 `role_families.RolePlaybook.outcome_metrics` **派生**，不另建一张表——
  两份清单一定会漂移。顺序沿用 playbook 原有顺序（它已经是「最强证据优先」，
  二次排序等于对同一个问题给出第二种意见）。
- `direction` 有五个取值：`down` / `up` / `scale` / `self` / `unknown`。
  `self` 指名字里已经含方向词（`风险敞口下降` 不能再生成「下降从 ___ 降到 ___」自相矛盾）；
  `unknown` 指认不出来，给中性的 `X：___` 而**不是**默认 `up`——
  默认 up 会「权威地」告诉用户错误率本该上升。
- 规则表顺序敏感：`错误率`/`差错率` 必须排在泛化规则之前，`覆盖率` 必须在 `覆盖` 之前；
  延迟类（ms/s）与周转类（天/小时）分开，否则 P99 配「天」读起来就是错的。
- 只有 `missing_outcome` / `unquantified_outcome` / `vague_quantity` 三种问题返回候选。
  `weak_ownership`（问的是担责程度）、`empty_experience` 等返回空——
  给它们挂指标句式等于问错了类型的答案。按 **kind** 门控而不是按 `quantification_optional`：
  法务/HR 的问题一旦问出来，答案仍然是数字。
- 前端点击是**追加**而非覆盖：一条 bullet 可以合法带两个数字，静默丢弃用户已输入的内容
  绝不是「点击建议」的正确解读。

## 4. 目标岗位对齐

绑定 JD 时允许三件事，仅三件：

1. 重排要点顺序，让相关经历前置；
2. 在**指同一件事**的前提下借用 JD 的词汇（源文 `服务治理` → `服务网格治理`，仅当源文确实是服务网格）；
3. 在 summary 中点明求职方向。

**不允许**因为 JD 要求就新增技能或经历。JD 是排序和措辞的依据，不是事实来源。

## 5. 三档优化强度的真实语义

档位控制的是**措辞离原文多远，而不是能否添加事实**。任何档位都不得新增事实。

| 档位 | 含义 | 适用 |
|---|---|---|
| 保守 | 贴近原文，只做语句通顺与结构整理 | 内推、已有背书，或对原措辞有把握 |
| 标准 | 按 Action + Object + Outcome 重写，补齐缺失的结果表述 | 默认推荐 |
| 强化 | 在证据上限内强化主导性与量化，突出最强成果 | 冲击更高职级 |

强化档的验收标准是一句话：**每条拔高表述都要能撑过面试官追问「这块能具体讲讲吗」**；撑不住就必须减弱。

### 6.1 手段标注为何是确定性的

`elevation_techniques.py` 通过比较**保守基线文本**与**写作结果文本**来给每处改动贴标签，不额外调用模型。理由有三：
无额外延迟与成本；标签不会与文本实际变化脱节；可被单元测试覆盖。

标签集合（id 为前后端契约，新增需两侧同步）：

| id | 展示 | 判定依据 |
|---|---|---|
| `quantified` | 补量化 | 结果文本出现了基线没有的数字/量级 token |
| `outcome` | 加结果 | 出现结果性标记词而基线没有 |
| `ownership` | 强化主导性 | 基线无 ownership 动词而结果有，或基线弱动词被替换 |
| `object` | 明确对象 | 结果文本出现了基线没有的具体系统/技术 token |
| `jd_aligned` | 对齐岗位 | 结果文本引入了 JD 关键词而基线没有 |
| `tightened` / `expanded` | 精简表达 / 补充细节 | 仅在上述均未命中时按长度比兜底 |

长度类标签只在其他标签都没命中时才上报，否则每次改写都会挂一个无信息量的标签。

### 6.2 兜底路径必须保持真实

`ResumeDraftBuilder._elevate_bullet` 是模型不可用时的规则兜底。它只允许**改写源文已有的内容**：
去除 `相关工作` 一类填充后缀、去掉 `做了` 一类空动词、把弱动词最多提升到 `负责`。

它**不得**追加结果、指标或规模。历史实现曾拼接 `，取得可量化业务成果`——这既是审稿器定义的阻断级错误，也会让用户在面试中失分。
`tests/test_resume_draft_builder.py::test_fallback_never_appends_an_unsupported_outcome` 锁定这条约束。

### 6.3 严重级别分层

审稿发现分两级，语义不可混用：

- `error`：最高级别发现，导出前必须让用户看见。无源支撑的事实、夸大 ownership、缺联系方式、
  日期不完整、占位符残留、空经历。
- `warning`：仅提示。缺对象、有证据但无结果、模糊量词、弱主动词、第一人称开头、超长 bullet、
  最强成果未置首。

未知或缺失的 severity 一律按 `error` 处理（fail closed），所以**任何新增的确定性检查都必须显式
标 `warning`**，否则会被升级成最高级别发现。实现见 `ResumeReviewer._has_blocking_issue`。

> 历史缺陷备忘：早期实现对"存在任何 issue"即判 `failed`，而新审稿指令会正常产出 warning，结果是用户永远无法导出。
> 改动 reviewer prompt 的 issue 产出策略时，必须同时确认分层逻辑。

#### 6.3.1 审稿是告知，不是门禁

**导出永不被审稿拦住。** 这一条优先于本节其余所有内容。

早期实现是双重闭门：前端按 `can_export` 禁用全部下载按钮，后端 `export()` 还会再跑一遍审稿、
不通过就抛 `AppError(code="reviewer_failed")`。结果是**一次模型调用成了产品核心交付物的单点故障**，
三种完全不同的处境都以「用户手里什么都没有」收场：

1. 审稿读了稿子并提出发现——有时是误报（把两条 highlight 合并会合法地破坏逐句归因，
   新增侧审计会把它报成无源断言）；
2. 网关不可达，**根本没有结论**；
3. 请求一直不返回——`flash` 场景是 3 个 endpoint × 60s 串行重试，用户最长盯三分钟转圈。

只有第 1 类是关于简历的陈述，而**连它也该由用户自己判断**。误判的代价 100% 落在用户身上，
而一个产品的全部工作就是把那个文件交到他手里。

**三态契约。**

`available` 与 `status` 回答的是两个不同的问题：「审稿读了稿子并发现无源数字」和「网关挂了」，
在旧实现里都以 `FAILED` 到达下游。所以 `ReviewerResult` 增加了 `available: bool`：

| 状态 | 含义 | `reviewer_status` 落库 | 用户看到 |
|---|---|---|---|
| `passed` | 读过，无阻断发现 | `PASSED` | ✓ 质检通过，可以导出 |
| `failed` | 读过，有发现（V1 为建议级） | `FAILED` | ! 发现 N 处建议先确认的问题 |
| `unavailable` | **没有结论**：网关挂 / LLM 未开 / 返回不可解析 / 输入超长 | `PENDING` | i 这次没有完成检查，不影响下载 |

`PENDING` 是「没人检查过」的诚实记录。存 `PASSED` 是撒谎；存 `FAILED` 日后会被读成
「这份稿被否了」，而它其实从未被读过。

**两类原因必须分开呈现。**

- **有发现（第 1 类）**：按知情同意处理。用户必须先看见发现，点一次「我已了解，仍要下载」才解锁。
  这不是 modal——目的是「看过」，不是「难走」。「回到优化预览修改」是 `btn-primary` 领先位，
  「仍要下载」是 `btn-ghost`：推荐改，但不强制。文案用「建议先确认」，不用「必须修改」——
  后者是我们并不兑现的承诺。
- **没有结论（第 2 类）**：**永不挡人，也永不呈现为简历的问题**。用户既没造成也修不了我们的网关，
  把它写成「你的简历有问题」是误导。此时 issue 列表**不渲染**——里面只有英文内部诊断
  （`reviewer_unavailable` 之类），会被读成简历缺陷。
- **一直不返回**：等待是提供的，不是强加的。转圈区给「不等了，直接下载」，点下去立即解锁；
  迟到的结果**不会重新锁住**已经放行的下载。

**与 3.6「不编造」的关系。**

两者不冲突，也不互相引用。3.6 约束的是**我们写什么**；本节约束的是**我们凭什么扣住用户的文件**。
放宽后者不等于放宽前者：写作侧依旧不编造，审稿依旧逐条核对并把发现讲清楚，只是不再替用户
决定他能不能拿到自己的简历。

**验收。**

`can_export` 字段保留且**恒为 True**，仅为契约稳定性（标记 deprecated）。这条不变量读不出来——
`downloadable` 由四处 state 合成，而回归是静默的：一个禁用的按钮看起来像是深思熟虑的决定。
所以它由 `scripts/verify_export_gate.py` 的三个真机 case 锁定，细节见 `QA-TESTING.md`。
`verify_resume_steps.py` 覆盖不到这里——它的夹具是「质检通过」，两次变异测试下都仍然 PASS。

### 6.4 篇幅估算是实测的，不是估的

`resume_diagnostics.py` 的 `_PAGE_BUDGET` 来自真实渲染：把我们自己的模板按递增长度渲染成 PDF，
记录 Chromium **实际**在第几个字符处分页（多段经历版式，计数前去掉空白）。

| 模板 | 第 2 页起始 | 第 3 页起始 | 采用常数（首页 / 后续页） |
|---|---|---|---|
| `zh-one-page` | ~1226 字 | ~2778 字 | 1200 / 1550 |
| `en-two-page` | ~1997 字 | ~4117 字 | 1950 / 2120 |

首页与后续页分开记，因为首页要放头部和 summary，容量更小；用单一平均值会把一份真正的两页简历
标成 1.6 页。改动模板字体、字号或页边距后，跑 `scripts/calibrate_resume_pages.py` 重新测量并更新常数。
该脚本需要 Playwright 的 Chromium，受限沙箱内无法运行。

## 8. 岗位族 playbook：不同岗位的"好简历"不一样

**问题**：本文第 2、3 节的方法论是按研发岗写的，然后被套用到所有人身上。这同时造成两个错误：

1. **服务不足**：读运营简历的人找的证据和读后端简历的人不一样。"产生了什么结果"在增长岗是留存和 GMV，
   在销售岗是赢单率和回款周期，在法务合规岗有时是"风险没有发生"——**根本没有数字**。
2. **主动惩罚**：审稿器会报「有证据但无成果」，手段标注用技术名词识别"对象"。两者都按研发词汇调过，
   所以一条写得很好的市场 bullet 会被判成空泛。

**解法**：`backend/server/src/jc/domain/role_families.py` 定义 16 个岗位族 playbook。
playbook 只提供**词汇与阅读顺序，绝不提供事实**——它可以说"增长岗要看留存影响"，
但永远不能提供一个留存数字。

| 字段 | 作用 |
|---|---|
| `outcome_metrics` | 该岗位合法的"成果"长什么样，用于向用户和写作模型提示该找什么证据 |
| `object_nouns` | 该岗位 bullet 的"对象"是什么，使非技术对象不被误判为空泛 |
| `quantification_optional` | 缺数字是真问题还是这份工作本来如此，决定审稿器**是否允许**报 `no_outcome` |
| `must_haves` | 通用审稿看不到的岗位硬要求（设计岗没有作品集链接就不是一份简历） |
| `section_priority` | 该族招聘方先读哪个 section |
| `framing_angles` | 诚实的重新表述角度：同一件事，换成这个受众在意的说法 |

`quantification_optional=True` 的族：法务 / HR / 财务 / 设计 / 通用知识工作。这些族下审稿器
**完全不得**因缺数字报问题，否则等于在教用户去编一个。

族 id 与 `backend/agent/prompts/coach/industry_followups.yaml` **共用同一套**，
所以简历写作和模拟面试对"岗位"说的是同一种话，而不是两套。

### 8.1 岗位族如何确定（优先级是刻意的）

`resolve_role_family()` 是唯一入口，优先级从高到低：

1. **用户显式选择**（`payload.preferences.role_family`）
2. 目标岗位已存的分类（`jc_job.role_category`，JD 解析时写入）
3. JD 标题，然后档案最近两段经历的标题

推断放在最后，因为**猜错等于整份简历按错误受众改写**，比用通用 playbook 更糟。
别名表里 `管理` 刻意排最后一位，所以"后端技术负责人"归 `backend` 而非 `management`。
前端在第 3 步的`WritingOptionsPanel` 提供下拉切换，改完问题与写作同时重算。

**写入口只有一个。** `payload.preferences.role_family` 只由 `PUT /writing-options` 写。
早先 `POST /evidence-answers` 也接受这个字段，而面板回传的是**推断出来的**族——
于是用户只要回答一条问题，一个猜测就被固化成了「用户的显式选择」，此后再也不会被重新推断。
`test_answering_never_writes_the_role_family` 锁住这条。

## 9. 证据补全：问，而不是编

`backend/server/src/jc/services/evidence_gaps.py` 做一次**确定性扫描**（无模型调用），
找出本该带成果却没有的要点，每条转成用户几秒内能从记忆里答出的问题。

| kind | 触发条件 | 问法要点 |
|---|---|---|
| `vague_quantity` | 出现 `多项`/`若干`/`大量` 等模糊量词 | 换成真实数字 |
| `weak_ownership` | 以 `参与`/`协助`/`配合` 起头 | **不预设用户主导**，给"独立负责/带人做/配合他人"三选 |
| `missing_outcome` | 有动作有对象，无结果 | 按该族 `outcome_metrics` 提示找什么 |
| `unquantified_outcome` | 有结果表述但无量级 | 仅对非 `quantification_optional` 族提出 |
| `thin_bullet` | 少于 10 字，只是个标签 | 请补充具体做了什么 |
| `empty_experience` / `empty_project` | 整段/整个项目没有任何要点 | 权重最高，最近一段更高 |
| `missing_must_have` | 族 `must_haves` 缺失（如设计岗无作品集链接） | 提示补链接 |

设计约束：

- 每条 bullet 最多出一个问题，按强度排序；近期经历权重更高。**已量化的强 bullet 不产生任何问题**，不骚扰用户。
- 非量化岗位不逼数字，改问"解决了什么问题/避免了什么风险/支撑了什么决策，没有数字也没关系"。
- `_THIN_BULLET_CHARS = 10`（曾设为 18）。18 会把"只是缺成果"的句子误判成"太短"，
  盖掉更有用的 `missing_outcome` 问题。

### 9.1 答案的信任等级

用户填写的答案写入 `payload.evidence_answers`，这是**用户亲笔的源事实**，因此：

- 写作模型可以把它当作与 bullet 同等的源材料使用（`resume_writer.md` 的 `user_supplied_evidence` 段）；
- 审稿器必须承认它是支撑，不得对其报 `unsupported_fact`（`reviewer.md` 的「What counts as source evidence」段）；
- 但审稿器仍然**阻断对答案的放大**：答案写"约 3000 QPS"而简历写"万级 QPS"，按无源事实处理。

实现上刻意**只追加、不改写**：答案与它所属的 bullet 分开存放，不去动用户自己写的文字。
原因是信任边界——模型不得自行修改已确认的档案（见 PRD-V1 的安全边界）。要点的实际融合发生在生成时，
由写作模型完成，且每次都可以重新生成。

`version` 照常递增，所以并发编辑仍会正常触发乐观锁冲突。

## 10. 投递前体检：会不会被读完

`backend/server/src/jc/services/resume_diagnostics.py`。审稿器回答"这份简历是否诚实"，
但没人回答"这份简历会不会被读"。这两件事必须分开，**只有第二个问题的答案可以阻断导出**，
体检结果一律是建议。

测量四项：

1. **岗位用词覆盖**：JD 的词哪些在简历里完全没出现；哪些**只出现在技能栏**而没有任何经历佐证——
   后者是面试中最容易被追问穿的地方。文案明确写了「没做过就不要加」，不能把缺口变成教用户造假的提示。
2. **估算篇幅**：见 6.4，用实测常数。
3. **要点条数**与**最长要点字数**：超过 160 字的 bullet 一眼读不完，提示拆成两条。
4. 过薄（< 0.6 页）时**指回证据补全**，而不是建议扩写——扩写无内容只会变成注水。

## 11. 包装角度：同一件事的几种真实讲法

同一段经历支持多个都成立的写法，而**先讲哪一个**，是决定招聘方是否停下来读的最大单一变量：

```
源材料：把订单服务从单体拆成 6 个微服务，耗时三个月，期间没有线上事故。

强调规模 → 覆盖 6 条业务线、日均 1200 万单的订单主链路
强调主导 → 独立出方案、定边界，推动三个团队按季度交付
强调结果 → 迁移期间零线上事故，发布耗时从 40 分钟降到 6 分钟
强调深度 → 为跨服务一致性设计补偿事务，放弃分布式事务方案及其原因
```

四种都是真的。在 `framing_presets.py` 之前，这个选择隐含在 prompt 里，用户看不到也改不了——
这正是「只有一个不透明的优化按钮、没有手段可选」这一感受的来源。

现有六个角度：`scope` / `ownership` / `outcome` / `depth` / `collaboration` / `jd_fit`。

| 约束 | 说明 |
|---|---|
| 最多 2 个 | 一个显得单调，四个等于没有重点。`MAX_EMPHASES = 2` |
| 顺序有意义 | 第一个为主角度，第二个用于主角度不适用的要点 |
| 空选 ≠ 无角度 | 回落到该岗位族的推荐组合。模型本来就隐含有角度，用岗位默认严格优于随机 |
| 只改呈现 | **不得新增事实、不得超出源文的动词强度、不得引入数字** |

最后一条是硬边界，且有一个具体的高危点：**`ownership` 不是把源文的 `参与` 改写成 `主导`**，
而是把源文确实记录了的「他做过的决策」提到前面。审稿器对「夸大主导性」的阻断**不因角度而放宽**，
`reviewer.md` 的「Framing angles」段显式写了这一点。测试 `test_framing_presets.py`
对每一个角度都断言边界文案随角度文本一起进入 prompt。

岗位族 → 推荐角度的映射（16 条）集中在 `framing_presets.py` 的 `_RECOMMENDED`，
而不是分散进各个 playbook：这是一个**产品判断**（这个受众先读什么），集中放便于一处评审。

### 11.1 这不是「丰富度」的解法

换角度不会让简历变长。要让简历更充实只有两条真路径：覆盖度（3.4）保证源文内容不丢，
证据补全（第 9 节）提供新的真实材料。前端文案明确区分了这两者，避免用户以为换个角度就能变厚。

### 11.2 写作侧的「让真实工作读起来有分量」

`resume_writer.md` 新增一段，要求每条要点检查源文是否已经包含而没写出来的四类材料：
**约束**（什么让这件事难）、**方法**（具体怎么做的、放弃了什么替代方案）、
**影响面**（触达多少服务/团队/市场/客户、持续多久）、**结果**（量化阶梯能到的最高一级）。

带上其中三类的要点读起来是资深工作；只有动作的要点无论动词多强都读起来像岗位说明书。
同一段同时写了反向约束：**四类材料必须全部来自源文**——写一个档案里没有的约束同样是编造，
只是更难被发现，所以更危险；且不得把一条要点膨胀成一段。

## 12. 覆盖度审计：生成稿是否真的留住了这份职业

`backend/server/src/jc/services/resume_coverage.py`。用户的抱怨有两种说法——
"内容太少了"和"跟工作经历极度不匹配"——指的是同一个缺陷：**生成稿比源档案薄**。三个成因：

1. 模型为了"精简"把两条无关要点合并；
2. 模型丢掉它认为弱的要点，而那恰恰是用户本可以补上数字的那些；
3. 模型整节漏掉 `project_blocks`，静默删除项目经历。

写作 prompt 三条都禁止了。**prompt 不是执行机制**：换模型、重试、档案变长，行为就会回来，
而且没人会发现——因为薄简历和薄经历在纸面上长得一模一样。

所以这里改为**测量**：对源档案每条 highlight，检查生成稿里是否仍有某条要点承载了它的内容。
匹配用**字符二元组包含度**（不是相等，因为改写措辞正是写作器的本职）：

| 参数 | 值 | 依据 |
|---|---|---|
| `_MATCH_THRESHOLD` | 0.42 | 改写后的要点通常保留源文 0.55–0.9 的二元组；同一段里两条真正不同的要点约 0.2。0.42 落在两簇之间的空带，普通改写与公司词汇共用都不会越线 |
| `_MIN_COMPARABLE_CHARS` | 6 | 更短的要点是标签不是内容，重叠度是噪声。按已覆盖处理——把"优化流程"报成缺失会让用户去找从不存在的内容 |

用包含度而非 Jaccard 是刻意的：写作器**本就应该增加**词（成果、规模、JD 用词），
Jaccard 会把这种增加当成损失来惩罚。我们只关心源文内容是否存活。

**刻意不设门禁。** 丢内容有时是对的：两条描述同一件事的要点**就该**合并，用户也可能主动要一页纸。
所以结果只呈现、不阻断，并把掉落的原文列出来，让决定权留在这份职业的主人手里。
唯一例外的严重情形是「档案有 projects 而生成稿 `project_blocks` 为空」——这从不是判断题，
一定是生成异常，文案直接建议重新生成。

暴露位置两处，职责不同：

- **第 3 步（优化预览）**：这里用户能动手——重新生成、换角度、答一条证据问题。
- **第 4 步（导出前）**：最后一道提醒，并提供返回第 3 步的入口。

在导出页才发现经历被丢已经太晚，所以不能只放第 4 步。

## 13. 第 3 步的版面约束（为什么文档要有自己一列）

方法论越完整，第 3 步能放的东西越多，而这一步最容易坏在**信息太多而不是太少**。
加完写作偏好、证据问答、覆盖度、篇幅提示之后实测：简历预览被推到距顶部 1082px，
也就是**用户打开第 3 步看不到自己的简历**。用户此前的原话是「不知道要干嘛」——
这正是那句抱怨的物理原因。

### 13.1 折叠只是延后问题，不是解法

第一版的解法是「建议面板默认折叠」。它把首屏偏移从 1082px 压到 707px，然后**在用户点开任一面板的瞬间失效**——
简历又被推下去，而点开面板恰恰是我们希望用户做的事。一个只在用户不使用功能时才成立的版面约束不是约束。

真解法是**给文档一列自己的空间**：`ElevatePreviewPanel` 接收 `rail` prop，
`ResumeStudio` 把写作偏好与证据问答作为 rail **传进去**而不是堆在文档上方。
实测首屏偏移 707px → 141px，且**与面板展开状态无关**。

### 13.2 为什么用容器查询而不是 `xl:` 断点

studio 与 agent 侧栏之间是**用户可拖拽**的分隔条。viewport 宽度无法描述这个面板实际有多少空间：
实测 1280px viewport 下 `xl:` 方案给出 **402px 的文档列**，比它要展示的简历还窄。

所以列规则写在 `globals.css` 的 `@container` 里（`.studio-columns` / `.studio-columns-inner` /
`.studio-doc` / `.studio-rail`），阈值 `@container (min-width: 60rem)` = 20rem 左栏 + ≈36rem 文档，
是 A4 预览仍可读的下限。DOM 顺序把控件放在前面（键盘与读屏顺序），`.studio-doc` 用 `order` 调整视觉顺序：
堆叠时 `-1`（文档在前），两列时 `2`。

### 13.3 两列必须各自滚动（`sticky` 是错的）

有了两列之后还剩一个缺陷，用户的说法是「用一个滑动控件，导致滑动控制出现错误」。实测证实：

| 元素 | 高度 |
|---|---|
| `.studio-doc` | 818px |
| `.studio-rail` | 2724px |
| 唯一真实 scroller | clientHeight 860 / scrollHeight 2756 |

一个 860px 的滚动容器装着两列，所以**一个滚动条推着两列一起走**，滚到左栏底部时简历已经
被推出自己那一列。`position: sticky` 不能解决——sticky 只在**包含块**仍在视口内时生效，
而包含块是整个 2724px 的 grid。

改法见 [`TECH-DESIGN-SYSTEM.md`](TECH-DESIGN-SYSTEM.md) §5.1：第 3 步外层 shell 自己不滚
（`stepOwnsScroll`），两列各自 `overflow-y: auto` + `overscroll-behavior: contain`，
grid 行用 `minmax(0, 1fr)` 约束。堆叠模式仍然**只有一个**滚动条。

两列**不做对齐**（实测首卡顶边差 47px，强行对齐只能填假空白），改做 focus 联动：
左栏问题获得焦点时，右侧预览把同一 `field_path` 的要点滚进视野并高亮。

### 13.4 量化门禁与它的自检

`scripts/verify_resume_steps.py` 分两种模式断言：

| 模式 | 断言 |
|---|---|
| 两列（`display: grid`） | `docWidth >= 600`；两列高度差 ≤2px；**无祖先在滚**；grid 自身不滚；左栏必须能滚；预览标签偏移 < 120px |
| 堆叠 | `docWidth >= 600` + 文档在控件**之前** + 偏移 < 400px |

两列那一行是**结构性**断言而不是距离。这很重要：上一版只断言像素偏移，而**坏版面同样能满足它**，
所以那个缺陷带着一个通过的门禁活了一整轮。现在的判据是「每列是否拥有自己的滚动条」，
坏结构无法伪装成好结构。

**两种模式必须都被执行到。** 1440×900 下 studio 面板只有 930px，低于 60rem 阈值，
单次运行**只会走堆叠分支**——两列规则（也就是这一步存在的理由）完全没被断言。
阈值在**容器**上，所以唯一办法是把窗口加宽：脚本现在会切到 1760×1000 再测一次，
断言确实进入两列模式，然后切回去。

**测量本身必须被自检。** 第 3 步里有两个嵌套的 `.scroll-area` 都包含预览标签，
取外层那个会把它的滚动位置混进来，一度得到 `-1279px` —— 而当时的断言 `offset < 400`
对这个垃圾值成立，于是脚本带着一项不可信的测量**通过了**。
现在：重置**每个** scroller、取**最内层**包含标签的那个、并断言 `offset >= 0`
——坏掉的测量必须响亮地失败，而不是悄悄通过。

**门禁要用变异测试验证。** 写完断言之后，把 CSS 故意退回 sticky 写法再跑一次：
脚本如期失败并报出 `the columns are 2079px and 818px tall; one is sizing to its content`。
没做过这一步的断言，无法区分「真的通过」和「根本没测到」。

### 13.5 左栏字号由测量守着，不靠评审

左栏字号规则有一个**在源码里看不出来**的失败模式：`.badge` / `.label-meta` 用
`@apply text-micro` 定义，而 Tailwind 的 `@apply` 会把**提到被 apply 类的每一条规则**克隆进去。
于是一条 `.studio-rail .text-micro { font-size: inherit }` 让编译器额外产出了
`.studio-rail .badge { font-size: inherit }`，badge 字号变成「取决于谁包着它」——
`div` 里 16px，`li` 里 12.5px。

`tsc` 不看 CSS，样式表源码读起来也完全正确，唯一能看见它的是浏览器里的 computed style。
所以 `_assert_rail_type` 直接量：左栏不得出现 13.6px 以上的文字、同一组件类不得出现两种字号、
总档数不超过 3（11 / 12.5 / 13.5）。完整机理与正确写法见
[`TECH-DESIGN-SYSTEM.md`](TECH-DESIGN-SYSTEM.md) §5.2。

### 13.6 结构化预览必须和导出一致

结构化视图此前丢掉两样东西，而它们都出现在导出文件里：

- **`scope_line`** —— 先总后分的那个「总」。它是角色摘要不是又一条成果，所以渲染成带左边线的独立一行，与要点区分。
- **整个 `project_blocks` 节** —— 于是「项目被提升到经历之前」这个决定在预览里完全不可见、却在导出的 PDF 里发生。

预览按 draft 自己的 `section_order` 排序，并把 `experience` / `experience_blocks` 归一为单个 token
（否则同一节渲染两次）。**预览与导出不一致是比预览丑更严重的缺陷**：它让用户确认了一份自己没看过的文档。

## 14. 新增侧不变量：生成稿有没有多说

`backend/server/src/jc/services/writing_invariants.py`。第 12 节测的是**丢**，这一节测的是**加**。
两者是不同的失败：丢内容让简历显薄，加内容让用户在面试里崩掉，而代价全落在用户身上。

加这一侧此前由两样东西守着，而**两样都不是测量**：

1. 写作 prompt 禁止编造。prompt 不是执行机制——重试、换模型、档案变长，行为就会回来。
2. 导出前审稿负责拦住。审稿本身是模型调用，所以"审稿会拦住编造"是一个**关于模型行为的假设**，
   测试套件里没有任何东西能验证它。

所以这里把它变成算术：给定已确认档案与生成稿，把每条要点归因回它改写自哪一行源文，
然后报告路上多出来的、源文从未说过的东西。

### 14.1 归因方向不能反

归因用的是和覆盖度**同一个**度量（`text_overlap`，字符二元组包含度），但**方向相反**，
这一点极易写错：

- **覆盖度**问「这条源文内容是否还在稿里」→ 要存活的是**源文**在草稿中的占比；
- **归因**问「这条要点是从哪行源文改写来的」→ 要存活的仍是**源文**，不是要点。

如果按「要点的二元组有多少能在源文里找到」来算，一条**正确地补上了成果**的要点会因为变长而
得分暴跌，于是每条写得好的要点都变成「无法归因」。所以 `text_overlap` 导出两个函数而非一个：
`best_match`（丢失方向）与 `best_origin`（归因方向），各自写明问的是哪个问题。

阈值也不共用。`_ATTRIBUTION_THRESHOLD = 0.30` 比覆盖度的 0.42 **更松**：覆盖度问
"内容是否还在某处"，严一点无妨；归因宁可拉进一个松匹配，也不要把一条改写过的要点当成无源之物。
真正匹配不上的要点单独报告——**没有可识别的源文行，是不调模型能拿到的最强编造信号**。

### 14.2 三类判定，以及为什么只有两类算编造

| 类型 | 级别 | 理由 |
|---|---|---|
| `unsupported_number` | 编造 | 数字在档案**任何位置**都找不到依据。检索范围是整份档案（含总结、技能证据、用户自填答案），因为写作器本就被要求把埋在别处的证据提到前面来 |
| `ownership_upgrade` | 编造 | 源文写参与类动词、稿子写主导类动词。这是最危险的静默改动：过了筛，面试里崩 |
| `unsupported_term` | 待看 | 英文术语不在档案里，可能是中文词的英文写法，也可能是新增技术栈声明。不调模型分不开，所以交给人判断 |
| `unattributed_bullet` | 待看 | 合并两条描述同一件事的要点是**合法**的，而合并一定会打断归因 |

两条刻意的豁免，都是因为朴素版本会误报正确写法：

- **日历年份不是指标。** `2021 年立项`来自档案的结构化日期，不是成果。
- **裸序数不是声明。** `第 2 期`、`Top 3`。但**带单位的数字一定查**——`6 条业务线`是规模声明，
  也是简历里最常见的夸张，而它没有 `%` 可以用来识别。这是 `_METRIC_RE` 必须认中文量词的原因。
- **邻近的主导表述算数。** 项目的 `role` 字段写着`技术负责人`，就确立了该项目 highlights 的主导关系。
  只看匹配到的那一行，会把"写作器正确使用了档案"报成升级。窗口刻意只取 ±40 字：
  隔三段之外的主导，不是**这件事**的主导。

### 14.3 它是探测器，不是门禁

每条判定都是**给人或给脚本的证据**，从不自动阻断导出。接入导出前质检时一律标为 `warning`：

- 确定性阻断会在写作器正常工作时触发（合并要点会改变归因），把用户锁在自己的文档外面——
  这正是 `_has_blocking_issue` 已经修过一次的缺陷；
- 审稿才是产品的门禁，它读得懂意图；这一层只证明一个更窄但更确定的命题：
  **这个数字、这个动词，在档案里找不到**。
- 审稿已经就同一条要点报过的问题会被去重，否则用户会用两种说法读到同一个缺陷。

## 15. 写作语义验收：模型真的做到了吗

`scripts/evaluate_writing.py`。JC 的验收脚本分层，而此前缺最后一层：

| 脚本 | 测什么 | 调模型 |
|---|---|---|
| `evaluate_documents.py` | 抽取质量 | 否 |
| `verify_resume_steps.py` | 前端运行时 | 否（mock API） |
| `e2e_smoke.sh` | HTTP 契约 | 是，但只断言结构 |
| **`evaluate_writing.py`** | **写作语义** | **是，且断言模型行为** |

产品关于**写作**的承诺全部由 prompt 约束、由模型判断。其中三条从未被测过：
换角度是否真换讲法；`ownership` 角度下审稿是否仍然阻断动词升级；覆盖度阈值在真实输出上误报多不多。

### 15.1 断言必须是差分的，不能是字面的

模型输出不可复现。断言措辞的脚本会在一次重试或一次换模型后变红，然后所有人学会忽略它。
所以只断言**任何正确输出都必须成立**的两条性质：

- **差异性**：两组不同角度必须产出实质不同的文本。`_SAMENESS_CEILING = 0.90`——
  取自覆盖度那条校准带的另一侧：同源的真实改写保留 0.55–0.9，所以两份**不同角度**的稿子
  还停在 0.9 以上，意味着角度没传到输出，而不是两份都忠实。相似度按**位置**比而不是最佳匹配比，
  因为角度本就允许重排，而最佳匹配会把重排过的稿子判成相同。
- **不变性**：任何角度下都不得新增无源事实或升级动词。这一条**委托**给第 14 节的确定性模块，
  脚本本身不重新实现规则。

**阈值校准只报告，不断言。** 真实输出上覆盖度报了 3 条，正确反应是人去读那 3 条字符串，
而不是构建变红。报告里把「刚好低于阈值」的近似命中单列出来：如果被标记的大多是近似命中，
说明阈值对真实输出偏严。

### 15.2 审稿门禁的压力测试

`framing_emphases` 会传给审稿，好让它不要把用户自己的排序选择报成缺陷。风险在于审稿
把角度读成**许可**。所以脚本在 `ownership` 角度的稿子里种一条已知坏要点——源文写参与、
稿子写主导——审稿必须仍然 failed。

种入的坏要点**从档案自己的文字派生**，只改动词（`inflate_ownership`）。
如果句子还有别的不同，审稿失败就不再能隔离出动词这条规则。

### 15.3 脚本自身被测

这个脚本只在网关可达处运行，也就是不在 CI。**永远通过的验收脚本比没有验收脚本更糟**，
所以它的判定函数由 `tests/test_evaluate_writing_script.py` 用手写草稿单测，
包括「相同稿子必须判为无差异」「真实换角度的稿子必须判为有差异」
「角度组合必须是合法 preset 且两两不同」——一个拼错的角度 id 会静默回退到岗位默认值，
于是脚本比较两份相同配置，然后把产品报成坏的。

隐私：样本是真人简历。报告只存测量值、判定和解释判定所需的短摘录，不存全文、不存联系方式。

## 16. 文档级重组：不改一句话，也能改一份简历

`backend/server/src/jc/services/resume_structure.py`。

第 2–3 节全部是**句子级**的手段。用户的原话是「只是简单地把每条描述优化了一下，
逐条优化文字而已，根本没有根本性提升，比如布局、描述整体结构、什么先总后分、结论先行之类的都没看到」。
这个批评是对的，而且它**不是「可以夸张」的变体**——它要的是结构性提升，与编造事实无关，
不能用第 3.6 节的理由去挡。

一份简历的强弱有三层，此前只做了最浅的一层：

| 层 | 问题 | 实现 |
|---|---|---|
| 句子 | 这句话有没有说清成果 | 第 2–3 节（已有） |
| 段内 | 最强的证据有没有排在前面 | `score_bullet` + `compose_document` 就地重排 |
| 文档 | 节的顺序、摘要形状、范围句 | `resolve_section_order` + `analyze_summary` + `scope_line` |

### 16.1 重组是零改写的

`compose_document` **就地重排 bullets 并重写 `section_order`，不改一句话**。
这是刻意的边界：重排没有事实风险，所以可以自动做；改写有，所以必须留给 writer 与审稿。
因此文档级重组既不需要模型，也不需要用户确认。

`score_bullet` 返回的 `is_lead_worthy` 阈值是 `>= 4.0`。节序调换**只允许一种**：
projects 提到 experience 之前，且需要 `_PROMOTION_MARGIN = 1.5` 的权重差——
一个会把任意两节换来换去的算法，产出的是让用户困惑的随机版式，而不是更好的简历。
`section_order_changed` 只在真有理由（`bool(reason)`）时为 True，因为「我重排了但说不出为什么」不该展示给用户。

### 16.2 `scope_line` 是源事实，不是派生

`scope_line` 回答「你当时负责多大的盘子」（团队规模、系统量级、业务范围）。
它**不能从要点推导出来**——只有用户知道自己带了几个人。所以它是 `ProfileExperience.scope` /
`ProfileProject.scope` 这两个档案字段，由用户在 `ProfileStudioEditor` 填写或由对话建档问出来。

实现细节有一个必须保留的约定：保存时空串**归一为 `null` 而不是 `""`**。
否则 `profile_intake` 会认为这题已答，再也不问——用户得到一份永远缺范围句的简历，却不知道为什么。

## 17. 岗位 blueprint：把「这类岗位的简历怎么写」变成可测的

`backend/server/src/jc/services/resume_blueprint.py`。

第 8 节的岗位族 playbook 回答「写什么」，但它只进了 prompt。用户因此说「不同岗位有不同的模板和方法论，我没看到呢」
——**只写给模型看的方法论，对用户等于不存在**。

blueprint 把同一套数字用在三处，这是它存在的全部理由：

1. **写给 writer**：`as_prompt_block()` 把章节顺序、摘要公式、分量要求写进 prompt。
2. **测生成稿**：`evaluate_blueprint(sections, role_family=)` 跑 6 项确定性检查。
3. **给用户看**：`BlueprintPanel.tsx` 展示「这类岗位的简历怎么写」+ 逐项检查 + 本稿的文档级改动。

同一套数字三处共用，所以**界面上的标准就是写作时的标准，也是检查时的标准**。三份各写一遍必然漂移。

### 17.1 六项检查

`REQUIREMENT_IDS`：`summary_conclusion_first`、`scope_lines`、`strong_lead_bullets`、
`document_depth`、`outcome_density`、`family_must_haves`。
族定义用 derive-then-override：先从岗位族 playbook 推默认值，再按族覆盖，
避免 16 个族各写一份 blueprint 后互相漂移。

默认常数：`_DEFAULT_LEAD_BULLETS = 4`、`_DEFAULT_TAIL_BULLETS = 2`、
`_DEFAULT_OUTCOME_RATIO = 0.6`、`_SOFT_OUTCOME_RATIO = 0.4`（量化可选的族用软阈值）。

### 17.2 一律 advisory

`unmet_issues()` 全部返回 `severity: warning`，和第 12、14 节同一个理由：
**任何确定性检查都不得把用户锁在自己的文档外面**。
reviewer 门禁 `_has_blocking_issue` 对未知 severity 按阻断处理（fail closed），
所以新增检查项时**必须显式标 warning**。

`resume_service._with_structure_issues` 把 blueprint 未达项追加在结构问题之后，
**按 code 去重**而不是按 field——多项要求合法地指向同一个 field 却说着不同的事。
顺序也是刻意的：blueprint 条目最宽泛（「分量与经历不相称」），放前面会埋掉它上面具体的发现。

### 17.3 `general` 必须说出来

`infer_role_family` 返回 `general` 意思是**「没认出来」而非「岗位是通用的」**。
推断**故意不猜**（有测试锁定），但沉默地落到 general 读起来像一个决定。
所以 `WritingOptionsPanel` 在 `role_family === "general" && !role_family_explicit` 时
显式提示「没认出你的岗位类型，正在按通用标准写」并给出选择入口。

## 18. 对话建档：空简历也要能产出文档

`backend/server/src/jc/services/profile_intake.py` + `intake_service.py`。

第 9 节的 `evidence_gaps` **入参是 bullet**——它能问「这条缺个数字」，但对一份空白档案无话可说。
而用户的场景正是「没有简历，或者很久没更新了」。这是 intake 存在的原因。

`classify_mode` 分四档：`empty` / `skeleton` / `stale` / `complete`，
`build_intake_plan(profile, *, role_family, answered_ids, limit=6)` 按 stage 产出问题，
`_DETAILED_ROLES = 2` 只详问最近两段经历（再往前问，收益不抵疲劳）。

### 18.1 关键不变量：计划问得完 ⇒ 一定能生成

highlight 问题的 id 最初按「还缺几条」的偏移量生成：答完 `highlight.0` 后列表变长，
下一题又被算成 `highlight.0`，随即被当作「已答」丢弃——**访谈永远停在距离可生成差一条的地方**。
这是产品缺陷而不是测试缺陷。

改为**按绝对 slot** 生成：`for slot in range(have, minimum)`，id `role.{idx}.highlight.{slot}`。
阈值 `_MIN_HIGHLIGHTS_LEAD_ROLE = max(_MIN_HIGHLIGHTS_PER_ROLE, _MIN_VIABLE_HIGHLIGHTS)`
——这个 `max` 就是不变量本身：最近一段被问到的条数**不可能低于**可生成所需的条数。

两条测试锁定它，并且**断言端状态而非常量**（否则两个阈值还会再次漂移）：
`test_the_plan_can_always_reach_viability`（含「没有任何问题被重复问」）、
`test_highlight_questions_keep_their_slot_as_answers_land`。

### 18.2 信任等级与无会话设计

intake 的答案和证据答案是**同一个信任等级**（用户亲笔，无模型介入），
区别只在于 intake 允许写**结构化字段**（`contact.name`、`experiences[i].scope`）——
一个填不进姓名的访谈永远产不出文档。

`apply_answer(payload, target_path, text)` 用固定处理表；**未识别的路径只存证据不写结构**。
`_answered_ids(payload)` 从 `evidence_answers` 里 `kind="intake:{qid}"` 的条目恢复进度，
所以**没有服务端会话**：刷新、换设备、隔一周回来都接着问。档案全程 `draft`，
用户仍要走确认流程——第 5 节的信任边界在这里不打折。

### 18.3 写入绝不静默，而且必须可核对

对档案的任何写入都要让用户看见——这是「不允许模型自行确认档案 patch」这条边界的用户侧对应物。
但第一版只做到了「看见」，没做到「可核对」，这不够：

> 已写入档案：experiences[0].scope、experiences[1].scope、preferences.target_roles

用户无法从这句话判断我们记下的对不对。**点路径是实现细节，泄漏到界面上就等于没有回显**——
回显存在的全部意义是它能被核对，而核对只能用用户认得的词进行。

所以 `describe_path(profile, path)` 把路径翻译成「某某科技 · 后端技术专家 · 负责范围」，
同一个函数同时用于**待答问题的「写入：」标签**和**写入回显**（两处必须一致：
问题说「在「某某科技 · 后端专家」」而回显说「experiences[0]」，读起来像两件事）。
`IntakeAppliedWrite` 同时带 `label` 和 `value`，所以回显是「字段 + 我们存下来的原文」。

未识别的路径**回退为原样输出而不是猜一个名字**：错的标签比丑的标签更坏，
它会让用户去核对另一个字段。

### 18.4 访谈必须可回改

答过的问题从 `questions` 里消失是对的（否则计划不终止、进度永远到不了 done），
但**从响应里完全消失就让访谈变成一次性写入**——用户看到 scope 被写了，却没有任何入口回看或改错字。

修法是把它们放进独立的 `plan.answered`，默认折叠在问题列表下方。
修改走**同一个** `intake-answers` 端点：服务端按 question id 归一，
所以重答是替换而不是新增一条。

这里暴露了一个真 bug，必须在放开回改之前修：`_apply_experience` 对 highlights 是**盲目 `append`**，
而计划用的是绝对 slot（`highlights[1]`）。于是用户修改第 2 条成果会**追加成第 3 条**，
原来的错字还留在纸面上。现在按 `target_path` 里的 slot 原地覆盖，
超出末尾则**钳制为追加而不是用空串补洞**——空的 highlight 在渲染出来的简历里是一个 bullet 形状的空洞。

两条测试锁定：`test_a_revised_highlight_replaces_the_one_it_corrects`、
`test_a_highlight_slot_past_the_end_appends_instead_of_leaving_a_hole`。
界面侧：未修改的文本不可提交（否则会无意义地递增 `profile.version` 并声称发生了什么）。
