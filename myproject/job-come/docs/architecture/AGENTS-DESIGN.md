# AGENTS-DESIGN：舟卡的智能体体系

- **状态**：设计草案，待确认后分步实施
- **最后更新**：2026-11-03
- **关联**：`TECH-AGENT.md`（权限边界）、`ADR-004`（分层 agent 架构）、`SPEC-MOCK-INTERVIEW.md`（面试辅导的功能规格）

## 1. 定位

舟卡由几个专业智能体组成，每个智能体对用户承担一个明确的承诺。会员购买的是这些智能体的能力，所以
智能体必须**可辨认、可解释、彼此独立**：用户能说出"这是简历智能体，那是面试教练"，每个都有自己的
工作方式、工具和边界。

## 2. 智能体清单

| 智能体 | 用户承诺 | 角色（DeerFlow） | 状态 |
|---|---|---|---|
| **简历顾问** | 把真实经历整理成招聘方看得懂的简历，并过质检 | `resume-coach`、`profile-interview`、`resume-writer` | 已有 |
| **面试教练** | 像真实面试官一样追问，给出有依据的修正和参考答案 | `coach-mock`、`coach-archive`，新增面试官 | 部分已有 |
| **评审官** | 独立旁观，给每一题打分并写报告；不提问、不参与对话 | `interview-reviewer`（新） | 新增 |
| **投递经理** | 针对一个岗位，走完从定制简历到准备材料的流程 | `apply-pipeline` | 已有，**需要收窄**（见 §6） |

"评审官"是面试辅导内部的独立智能体，不对用户单独售卖。

## 3. 隔离规则

隔离是这套设计最重要的约束。下面的规则要写进代码和测试，而不只是文档。

**R1 — 每个智能体的技能和工具由声明固定。** 每个角色在 `backend/agent/roles.yaml` 中声明自己的技能、工具、运行方式和模型场景（`jc.agent.roles` 加载）。任何角色的范围都**不得包含另一个产品智能体的技能**。测试检查这一点。

**R2 — 跨智能体协作只通过工具，不通过合并技能范围。** 定向申请需要定制简历时，它调用 `jc_apply_pipeline`，由服务端
在自己的权限下调用简历服务；它自己的技能里不放 `resume-writer`。

**R3 — 一个智能体调用另一个智能体，必须以"子任务"的形式**：子任务运行在被调用者自己的角色和工具范围里，结果以结构化数据返回。
评审官就是这样被面试官调用的（`jc_mock_review`），评审官的范围不包含提问工具。

**R4 — 技能 ID 全局唯一。** 同一个 ID 只能存在于 `skills/public` 或 `skills/custom` 之一。当前存在重名（见 §6），
需要消除，并用测试守住。

**R5 — 数据边界。** 每个产品的工具只写自己的表：简历写 `jc_resume_*`、`jc_profile_*`；面试写 `jc_mock_*`、
`jc_interview_*`、`jc_question_*`。读取共享的档案（`jc_profile_get`）是允许的，写共享表要经过所属服务。

**R6 — 商业规则在服务里，不在智能体里。** 额度（每月一场完整模拟）、导出水印、会员判断都由服务层执行，
智能体只能请求，不能绕过。

## 4. 各智能体设计

### 4.1 简历顾问（已有，保持不变）

- **技能**：`resume-coach`（对话与编辑）、`profile-interview`（建档访谈）、`resume-writer`（写作与优化）。
- **评审**：导出前的质检是独立的 `jc_resume_review` 工具，已经是"导出闸门"，不由写作智能体自己判断。
- **模型场景**：`writer`（写作链）、`coach`（对话）。

### 4.2 面试教练

- **面试官（`coach-mock` 技能，四种风格的说明写在同一个文件里）**
  - 职责：开场、按所选风格提问、追问、换题、收尾。决定问什么和怎么追问。
  - 风格：四种（温和引导、标准、压力、业务深挖）。风格只改变提问方式和语气，不改变题目覆盖和评分标准。
  - 工具：`jc_profile_get`、`jc_job_fetch`、`jc_bank_search_questions`、`jc_question_upsert`、
    `jc_mock_plan`（只读：覆盖情况与建议，不强制）、`jc_mock_ask`（登记提问，超限拒绝）、
    `jc_mock_end`（结束，缺口未补则拒绝）、`jc_mock_review`（交给评审官）、`jc_mock_session_history`。
  - 守卫在工具里：题数上限、追问上限、覆盖、额度。面试官可以判断，但规则不能被绕过。
- **评审官（`interview-reviewer`，独立）**
  - 职责：逐题五维打分并附证据（引用用户原话）；给出合理答案和修正；写整场报告。
  - 限制：**不能提问**，**看不到面试官的计划或推理**，只读整场问答和档案。
  - 工具：`jc_profile_get`、`jc_mock_session_history`（只读）、`jc_mock_report_write`（只写报告）。
  - 引用校验：参考答案里的每个事实必须能在档案中找到出处，由工具校验；找不到的标为"待补充"。
  - 模型：可配置（见 §5）。
  - 运行方式：评审官是一次独立的智能体运行（`review_session`），由 `jc_mock_review` 启动。只有这一条路径产生报告，报告由 `jc_mock_report_write` 写入并经服务端校验；服务不直接调用模型。

### 4.3 投递经理（收窄）

- **技能**：只保留 `apply-pipeline` 自己的说明。
- **简历与岗位能力**：通过工具调用——`jc_job_parse`、`jc_fit_score`、`jc_apply_pipeline`（服务端完成定制简历）。
- 现在它的范围包含 `resume-writer` 和 `resume-reviewer`，属于违反 R1/R2，需要改掉（见 §6）。

## 5. 模型配置

模型按**场景**配置（`backend/agent/llm/routing.yaml`），不按智能体写死。场景与智能体的对应：

| 场景 | 用途 | 默认 |
|---|---|---|
| `coach` | 面试官的对话 | 对话模型 |
| `reviewer`（新） | 评审官（模型 `jc-reviewer`，在 `agent/deerflow/config.yaml` 中声明） | 独立配置，不与面试官共用同一模型 |
| `writer` | 简历写作 | 写作链（已有） |
| `ingest_fast` | 结构化抽取 | 快速模型（已有） |

评审官用不同模型的价值：报告不由面试官的同一套判断产生，可信度更高。成本上，评审是一次独立调用，按场次计费。
默认沿用同一模型，需要更高可信度时在配置里换成另一个。

每个场景的 `llm_call` 记录都带上场景名，因此可以统计每个智能体、每场模拟的真实成本，用于会员定价。

## 6. 现有代码的问题（已修复，第 1 步）

1. **定向申请越界**（已修复）：`apply-pipeline` 不再包含简历写作与评审技能，工具中去掉了照片设置和评审工具。
   简历工作通过 `jc_apply_pipeline` 在服务端完成，闸门结果写在草稿的 `reviewer_status` 中。
2. **重名技能**（已修复）：`coach-mock` 与 `resume-reviewer` 的自定义副本被公共版本遮住，已删除；
   `apply-pipeline` 从 `custom` 移到 `public`，因为它是自有技能，不是需要审查的外部技能。
   隔离测试守住"技能 ID 只出现一次"。
3. **面试辅导缺少守卫工具**（已修复，第 3 步）：`jc_mock_plan / ask / end / review` 已实现，限制与覆盖规则由工具执行，
   超限或缺口未补的调用被拒绝并返回原因，不写入。这是 `SPEC-MOCK-INTERVIEW` 第 13 节的主要工作。

## 7. 对用户的承诺与会员

- 每个智能体在菜单里有自己的入口和一句话的承诺（已有的"准备/行动/复盘"分组可以沿用）。
- 免费与会员的差别按智能体划分，写在产品页上，而不是藏在按钮后面：
  - 简历：免费可优化与预览，导出带水印；会员无水印、不限次数。
  - 面试辅导：热身不限；完整模拟免费每月 1 场，会员不限。
- 面试辅导的完整模拟是会员价值的主要卖点，因此报告页要清楚展示"这份报告是评审官独立给出的"，让用户相信它。

## 8. 实施顺序

1. **隔离修复**（不改功能）：去掉 `apply-pipeline` 的越界技能；消除重名；加上 R1、R4 的测试。
2. **评审官与场景配置**：`interview-reviewer` 角色、`reviewer` 场景、`jc_mock_report_write`。
3. **面试官的守卫工具**：`jc_mock_plan / ask / end / review`，沿用第 1、2 步已完成的额度与覆盖逻辑。
4. **面试官的对话与风格**：`mock-interviewer` 说明、四种风格、端到端的模拟替身测试。
5. **报告页与归档**：`/mock-reports/{id}`，计入面试归档与战役统计。
6. **外部知识检索**（可选）：作为面试官与评审官的只读工具接入，不写入用户档案。

每一步都有测试，并可单独上线。

## 10. 对外命名（已确定）

"简历优化智能体 / 面试辅导智能体 / 定向申请智能体"是描述性的名字，不便于记忆和传播。给出三组方案：

| 方案 | 简历 | 面试 | 申请 | 评审（内部） | 特点 |
|---|---|---|---|---|---|
| **A 职业顾问（推荐）** | 简历顾问 | 面试教练 | 投递经理 | 独立评审 | 角色清楚，三个名字都是用户熟悉的职业词，"教练"直接表达陪练价值 |
| B 人名 | 小舟 · 履历 | 小考 · 面试 | 小投 · 申请 | — | 亲切，但对外专业感弱，和"专业智能体"的定位有出入 |
| C 功能 | 履历工坊 | 面试实验室 | 投递战役 | — | 与现有菜单"战役看板"呼应，但名字偏工具，不像智能体 |

**已确定方案 A**，对外总称"舟卡职业智能体"。会员页可以逐个介绍：简历顾问负责经历的整理与优化，面试教练负责模拟与复盘，投递经理负责针对岗位的申请流程。
评审官只出现在报告里（"独立评审给出"），不单独作为产品名。

正文已统一使用正式名称；描述性名字只在本节作为备选记录保留。

## 11. 设计借鉴

以下借鉴的是**设计原则和结构**，不照搬人设文本、角色口号或风格描述。

| 借鉴的内容 | 对应本文档的部分 | 怎么改 |
|---|---|---|
| 评估—优化循环：评审方用不同的评分框架；硬性的最大轮数；同分连续不提升则停止并上报 | `engineering/engineering-multi-agent-systems-architect.md`（模式 4） | §4.2 评审官；§13 修订 | 报告的修正阶段最多一轮；评分连续两次不变则标注"待复核"，不循环 |
| 最小权限矩阵：每个角色列出能读、能写的数据 | 同上（"最小权限"一节） | §3 R1、R5 | 用表格把各智能体的读写权限写清楚，作为测试的依据 |
| 何时拆分智能体：一个智能体做两种不同的认知任务，就拆开 | 同上（"何时拆分"一节） | §2 拆分理由；§4.3 申请智能体 | 面试官与评审官拆开；申请智能体不再包办简历写作，改为调用简历顾问 |
| 简历不编造：不添加档案中没有的职位、学历、指标或结果 | `specialized/resume-tailor.md`（关键规则 1） | §4.1 简历顾问 | 已有，补充"指标缺失时提问，不填数字" |
| 每处重写都说明改了什么、对应哪条要求、为什么更好 | 同上（规则 6） | §4.1 简历顾问 | 简历输出增加"修改说明"列表 |
| 不保证面试或录用结果 | 同上（规则 7） | §7 对用户的承诺 | 会员页与营销文案都不做结果承诺 |
| ATS 友好：不用表格、图形、复杂分栏 | 同上（规则 4） | §4.1 | 作为 PDF 模板的检查项 |
| 面试评分表要有行为锚点 | `specialized/recruitment-specialist.md`（面试流程设计） | SPEC §6.1 | 已补入三个参照点与评分规则 |
| 按岗位和资历分题库 | 同上 | SPEC §3、§4 | 难度作为面试官风格之外的维度，由 JD 资历决定 |
| STAR 追问：按胜任力维度准备追问 | 同上（行为面试） | SPEC §4 追问 | 追问必须引用用户上一条回答中的具体内容，并按 STAR 缺口选择 |
| 技术岗评估维度：基础知识、问题解决、系统设计、代码质量 | 同上（技术面试） | SPEC §6（技术岗） | JD 为技术岗时，追加对应的技术维度，报告中单独列出 |
| 面试官说话少于用户：60/40 原则 | `sales/sales-discovery-coach.md`（教练原则） | §4.2 面试官 | 面试官的指令中加入"用户发言应占大部分" |
| 停顿是工具：追问后留出时间 | 同上 | §4.2 面试官；SPEC §3 温和引导 | 温和风格的追问后不催促 |
| 先复述再追问，"不是审问" | 同上 | SPEC §3 | 追问话术模板：复述用户的具体说法，再问一个具体的问题 |
| 不问可以自己查到的问题 | 同上 | §3 R5、§4.2 | 面试官只使用简历和 JD 中的事实提问 |
| 分级标记：🔴 必须修正、🟡 建议、💭 细节 | `engineering/engineering-code-reviewer.md`（评审格式） | SPEC §7 报告 | 报告的修正分为"必须修正 / 建议 / 细节" |
| 具体、说明原因、给建议而不是命令 | 同上（关键规则 1–3） | SPEC §7 修正 | 修正写法统一：指出具体句子，说明为何不准确，给出建议写法 |
| 一次给完整反馈，不分散多轮 | 同上（规则 6） | SPEC §7 | 报告只生成一次 |
| 肯定做得好的地方 | 同上（规则 5） | SPEC §7 | 报告每题都先写一句用户答得好的地方 |
| 质量闸门：每个任务必须通过验证；重试上限 3 次，超过则升级 | `specialized/agents-orchestrator.md`（质量闸门） | §3 R6；SPEC §13 守卫 | 守卫工具超限返回"需要人工复核"，不静默通过 |
| 交接必须带完整上下文 | 同上（交接） | §13.2 | 评审官收到整场问答与档案，但不收到面试官的推理 |

**不借鉴的部分**：外部开源集合中多数角色是提示词人设（身份、性格、口号、表情符号），没有工具和权限边界。我们的规则由工具保证，
这一点是这套设计区别于人设型智能体的地方，不能因为借鉴而削弱。
