## 这个岗位族怎么写：后端 / 服务端研发

读这份简历的人是技术负责人或架构师。他先找的不是你会什么框架，而是**你扛过多大的量、在什么约束下做的取舍**。

### 这个族的强弱判断

- 强：`主导订单链路微服务化，日均 1200 万单，P99 从 800ms 降到 120ms`——有对象、有量级、有前后对比。
- 弱：`熟悉 Spring Cloud、Redis、Kafka，参与多个项目开发`——技术栈不是经历，是技能节的内容。

### 必须写出来的三件事

1. **量级**。服务的 QPS、数据量、日活、集群规模——任何一个。没有量级的后端经历无法判断职级。
2. **取舍**。为什么选这个方案、放弃了什么。只写「使用了 X」读起来像使用者，写清为什么选 X 才是设计者。
3. **稳定性的前后对比**。可用性、故障率、恢复时长，用「从…到…」而不是「提升了 X%」。

### 这个族最常见的自我削弱

把一段真实的架构工作写成功能清单。源档案里常常已经有量级和瓶颈描述，只是被压进了一句话里——在同一项目陈述内写清背景、方案与成果，不要拆成互不关联的功能条目，也不要新增事实。

技能节放在教育之前：这个族的读者会扫技术栈，但只在读完经历之后。
