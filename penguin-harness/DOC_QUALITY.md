# doc-sn 写作质量标准（Penguin）

> 凡改 `penguin-harness/doc-sn/`，必须满足本文。  
> 背景：DSH doc-sn 曾出现「流程图单调、新词堆砌、看不出封装边界」——Penguin **禁止重演**。

---

## 一篇合格文档至少包含

1. **实体 / 模块边界**  
   - 用表写清：`拥有什么 | 不拥有什么 | 依赖谁 | 禁止渗入什么`  
   - 至少覆盖本篇讨论的核心对象（缺表 = 不合格）

2. **写入归属**（流程类文档强制）  
   - 每一步写：谁执行、改谁的内存、落哪份磁盘/事件  
   - 禁止：「然后系统继续处理」而无主语

3. **熟悉对照**  
   - 每个首次出现的产品新词：一句话 + 接近的旧知识 + **不是什么**  
   - 禁止：只给英文名不解释

4. **固定算法 vs 扩展点**  
   - 写死在 ContextEngine 里的，明确说「改源码级」  
   - 可换端口 / 文件 / 回调的，单独成列  
   - 禁止：把固定 while 包装成「全插件」话术

5. **顶层意图（架构章强制）**  
   - 开篇回答：要解决什么、故意不解决什么  
   - 禁止：一上来就 mermaid 却无设计目标

---

## 明确禁止

| 禁止 | 反例 |
|------|------|
| 只有时序图/流程图，无实体表 | 「见下图」然后结束 |
| 名词墙无对照 | 连续抛 OmniMessage、MergeQueue、carry-over 无比喻 |
| 伪深度 | 「高度解耦、可扩展」而无边界 |
| 把表面当内核 | 教人改 Web 来「换 ReAct」 |
| 照抄 DSH 心智 | 写 Profile/Bundle/Cordis/Inbox splice 当 Penguin 概念 |

---

## 推荐章节骨架（顶层 / 子系统）

```text
1. 设计目标与非目标
2. 实体边界表（拥有/不拥有/协作）
3. 协作过程（逐步 + 写入归属）
4. 扩展点 vs 固定内核
5. 新词对照（若本篇引入新词）
6. 改代码决策树
```

流程专篇可把 3 放前面，但 **2 不能缺**。

## 与「00」的关系

- [00-顶层设计与实体边界.md](./00-顶层设计与实体边界.md) 是本标准的示范篇。  
- 其它文档补细节时，**不得与 00 的边界表打架**；若源码变了，先改 00 再改分册。
